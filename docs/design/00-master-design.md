# 总体设计：产品定位与设计原则

AI Editor 是一个面向小说创作者的辅助工具。核心命题：**AI 是创作顾问，不是代笔。**

- AI 帮助作者管理创作要素、探索剧情可能性、发现设定矛盾
- AI **不生成正文**——正文永远是作者的事
- **正文在系统内书写，但笔不离手（2026-09）**：章级正文由作者在本应用内书写（块编辑器，自动保存、随书备份、可导入导出）；AI 侧**只读**正文（按需读取 + 聚焦章注入节选），**没有任何写入正文的工具**，只能给建议
- 角色类比：AI 像是坐在你身边的资深编辑，帮你推演可能性、提出挑战性问题，但笔始终在你手里
- **分发形态（2026-09）**：桌面安装包（Electron 外壳，双击即用）与 npm CLI（`npx ai-editor` + 浏览器）**并存**，两者数据语义与服务行为完全一致——桌面版只是外壳，不引入第二套后端或第二种数据模型（设计见 `50-desktop.md`）

# 四大核心设计原则

## 1. 本地优先，数据主权归用户

所有创作数据存储在本地文件系统（`project.json` + `data.db` + `outline.json` + 项目目录 `sessions/`），**默认不上传云端**。AI 对话时仅将必要上下文发送给模型 API，对话历史在本地保存（模型 API key 不入项目文件）。用户可以随时导出完整项目数据，不被任何平台锁定（**导出/备份/云端的包 = 三文件；对话历史 `sessions/` 是纯本地目录、不进包**——2026-09 口径：会话含大量重复内容，进包会让体积不受控增长）。

**云端存档是可选加项（2026-09）**：用户可自愿把备份 zip 推送到自己的云盘（WebDAV），以获得异地副本与多设备续写能力。**它不改变本地优先**——云端是副本而非事实源；关闭后全部功能可用（离线可用优先）；不使用任何自建后端（传输层只有 WebDAV，其他云盘由用户自建 `rclone` / AList 桥接）；不提供平台账户体系；不锁定数据（云端目录随时可删）。凭据只落本机创作根的 `.ai-editor/cloud.json`（明文 + 权限 0600），**不进项目文件与备份包**。设计与不变式见 `40-cloud-sync.md`。

## 2. AI 作为思考增强，而非内容生成

与市面上「一键生成小说」的工具不同，AI Editor 的 AI 角色是**参谋**而非**写手**。这体现在三个交互模式上：

| 模式 | 交互 | 示例 |
|------|------|------|
| **问答式** | 用户主动向 AI 提问 | 「这个魔法体系有什么漏洞？」 |
| **反诘式** | AI 读取设定后主动抛出挑战 | 「如果灵脉会枯竭，底层平民为什么还留在那里？」 |
| **路径推演** | AI 基于已有节点推演可能的剧情线 | 「从『被逐出师门』到『修仙界至尊』有三条路径…」 |

> **正文边界（2026-09 修订，取代 2026-08 版）**：正文进系统——**储存、编辑、备份、导入导出都在本应用内完成**（章级块文档，真相在 `data.db`；参考资料同款）。AI 的读写边界是**非对称**的：
>
> | 方向 | 界限 |
> | :--- | :--- |
> | **读** | 允许：正文/参考资料入选 AI 上下文（工具按需拉取 + 聚焦章注入节选，受单条结果截断与分页约束） |
> | **写** | **禁止**：工具面不存在任何正文或文档写工具（结构性保证，不靠提示词）；AI 只能就正文提出建议，落笔永远由作者完成 |
>
> 因此「正文可被引用进对话」是**受控的只读能力**，而不是把创作决定权交给模型；`xl-*` 一类「AI 直接改写文档」的第三方能力一律不引入（见根 `AGENTS.md`）。

> **拆解小说（2026-09）**：用户提供既有小说文本（`.txt`）→ 建项目 → LLM 把它整理成结构化创作数据（大纲 + 章正文 + 人物/设定/地点/关系 + 拆解报告）。它是**导入式批量管线**而非对话能力：模型仍然没有任何写工具，只产出结构化 JSON，落库由服务端确定性代码完成；「开始拆解」= 用户对整批导入的**一次性授权**（与「导入备份」同类，不走提案仓）。原文进系统属于**用户提供的数据**，不是 AI 生成——与上表的读写边界不冲突。阶段、调度、幂等与不变式见 [`60-decompose.md`](./60-decompose.md)。

## 3. 创作要素的结构化管理

长篇写作的核心痛点是「写到后面忘了前面」。解决方案是将四类创作要素统一建模：

```
人物 (Character) ─┐
设定 (Setting)  ──┼── 通用关系表 ── 大纲节点 (Plot Node)
地点 (Location) ──┘
```

四要素之间通过一张**通用关系表**互相关联，支持紧邻查询、k 跳查询（**深度上限 3**，REST `depth` 参数 `min(1).max(3)`）。从任意一个实体出发，可以找到与之相关的创作要素。

## 4. 结构体先行，AI 填入

所有创作要素都有预定义的结构（人物档案模板、设定分类树、大纲层级），用户先在结构框架中填写内容，AI 在已有结构基础上做语义分析和建议。这避免了 AI 自由发挥导致的失控。

# 竞品对比中的差异化

| 维度 | 竞品现状 | AI Editor |
|------|---------|-----------|
| 数据主权 | 云端或平台绑定 | 本地优先，文件系统（云端存档为**可选**异地副本，可随时停用） |
| AI 角色 | 生成正文为主 | 推演 + 反诘；可读正文（只读），不生成、不改写正文 |
| 关系管理 | 各自独立的关系表 | 通用关系表，k 跳查询 |
| 变化追踪 | 无或手动记录 | Delta 累积自动回溯 |
| 人物-剧情 | 单向（人物驱动或剧情驱动） | 双轮驱动，互相喂养 |
| 平台绑定 | 阅文、橙瓜等绑定发布平台 | 完全不绑定 |
