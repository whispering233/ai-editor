# 数据模型与存储详细设计

> **本文档职责**：回答「数据为什么这么设计、哪些不变式不可违背」——存储双轨、统一模型、Delta 语义、软删级联、schema 演进、备份命名等约束与理由。
> **结构契约**（字段/表/文件格式的「是什么」）见 `docs/db/schema.md` 与 `docs/api/` 各模块端点文档；本文档只讲语义与不变式，不重复字段清单。
> 已过时/被修订决策的完整历史原文可由 `git log` 回溯，本文档只收录**仍生效**的契约。

## 1. 存储双轨：三个数据文件，不强行统一

系统数据落在四种载体（三个文件 + 一个目录），各司其职，**不要试图统一**：

| 文件 | 内容 | 格式理由 |
| :--- | :--- | :--- |
| `outline.json` | 大纲树（整树 JSON） | 天然树形结构，整树读写、无需拼接 |
| `data.db` | 实体/关系/Delta/**块文档**（SQLite） | 需要结构化查询、关联追踪、Delta 累积计算；块文档（章正文/参考资料载荷）与实体同库事务读写 |
| `sessions/` | 对话历史（一 session 一 JSONL，格式由 pi 定义） | **纯本地目录**：随书目录改名/移动，但**不进任何 zip（备份/导出/云端）**；追加写、可读可 diff；行格式 = pi session v3（消息/压缩/模型变更等 entry），本仓不定义、不解析行结构 |
| `project.json` | 项目配置（id/name/language/schema_version/current_position 等） | 轻量元信息，与大纲同款原子写 |

**不变式**：大纲树与剧情图是**同一数据的两种投影**（树与图共享同一数据中心），不是需同步的两份数据——图上的剧情连线是关系数据 `plot_edge`，不是独立存储。**画布 UI 已移除**（2026-08），`plot_edge` 数据能力保留（分析类工具仍可多线推演）；节点坐标与缩放**不入任何存储**（客户端 localStorage 只有主题 `ai-editor:theme`、三栏面板 `ai-editor:panels`、写作偏好 `ai-editor:writing` 与大纲页视图 `ai-editor:outline-view`）。

**块文档载荷单一存放点（2026-09）**：块编辑器承载的长文本（章正文、参考资料正文）统一存 `document_records`（`owner_kind` = `chapter` | `reference`，见 §13），实体自身的短字段仍在 `entities.data`（判定标准：**块文档编辑器承载的长文本 → 文档表；参与 Delta/筛选/摘要的结构化短字段 → 实体 data**）。章正文不进 `outline.json`（整树接口不能被长文本拖累），也不再有项目目录内的正文文件。

## 2. 大纲树：严格三层，无游离节点

- 固定三层 **volume（卷）→ chapter（章）→ scene（场景）**；创建必须显式指定 `parent_id`：volume 挂 root、**chapter 只能挂 volume**、**scene 只能挂 chapter**，无默认值。
  - **章只挂卷（2026-09）**：`root` 仅接纳卷——“根级章”（不属任何卷的章）使「卷末章」「章序前缀」类推导多出一条分支，而写作现实里章总归属某卷。**收紧仅限写入**（`db.assertCanHold` 单点 + 提案层/工具描述 + 前端 `parentOptionsForType` 三面同口径）；**存量根级章读容忍**：能渲染/改名/删除/拖进卷，但不能再新建、也不能再移回 root（无迁移）。
- **不存在游离节点**（无 `orphan_nodes` 机制）——游离节点制造「树外状态」的语义裂缝，状态计算、软删级联、提案快照都要为它开特例；取消后树路径唯一、规则单一，全链路简化。
- 节点带 `updated_at` 版本戳（任何字段变更时由服务端原子写统一更新），顶层带 `schema_version`。节点级 `updated_at` 同时支撑提案快照比对（见 `30-agent-loop.md` §2）。

## 3. 通用关系表

**不按实体类型分表**：一张 `relation_records` 统一管理所有跨实体关系（人物↔设定↔地点↔大纲节点↔事件等，含 `plot_edge` 剧情连线）。理由：

- 新增关系类型只需扩展常量，不需要改表结构（`relation_type` 无 CHECK，连迁移都不用）；
- AI 分析时一次查询拿到全图，从任意实体出发查「所有关联」是一个查询。

**关系类型分层（2026-09）**：

- **属性单一来源 = shared 关系类型属性注册表**（`label` / `group` / `symmetric`，`Record<RelationType, …>`）——一张表取代此前散在各处的手写清单（client 中文标签表、人物页人↔人 5 类子集、对称类型清单、对话框排除集）。加关系类型 ⇒ 必须补属性，否则编译失败。
- **自定义类型（轻量口径）**：作者可在建立关联时输入新类型；类型**只活在数据里**（`relation_records.relation_type`），下拉从「预定义 ∪ 本项目已用类型」派生，不建表、不加管理 UI。语法校验单一来源 = shared 纯函数（REST / db 守卫 / client 预校验共用）。
- **AI 侧有意收窄**：`query_relationships` / `propose_add_relation` 的 `relation_type` 仍是**预定义枚举**——AI 不能造类型（防止 LLM 输出语义碎片），但**读**到自定义类型不拦。分层理由同 REST 泛型口径（§14 不变式 1）。

**Delta 不在此表**——独立存 `delta_records`（不侵入大纲 JSON 结构，因此无法表达「树外」状态）。

## 4. Delta 变更追踪与状态计算

人物/设定的属性是演化中的（主角黑化、战力从 100 涨到 850），**不采用版本快照**，采用事件驱动 Delta：大纲节点记录自己**引发了什么变化**。到达任意节点的状态 = 初始 `data` + **「章序 ≤ 目标进度章」的全部已确认 Delta**（章序前缀累积，2026-09 修订；详情见下文 §4 computeState 不变式）。

**computeState 不变式**：

- **章序前缀累积（2026-09 修订，取代“只沿父链”）**：状态 = 实体初始 `data` + **「章序 ≤ 目标进度章」的全部已确认 Delta**（跨卷、跨章累积），按（**章序**、节点内 `order`）双层排序——章序 = 全局先序遍历章序号（跨卷连续累计），树序即阅读序，节点 move 后下次计算自然反映新序。
  - **目标节点 → 进度章的映射**：`chapter` → 自身；`scene` → 所属章；`volume` → 该卷**最后一个未软删章**（无章 → 初始值）。**`root` 不能作 `at_node`**（节点查找只搜 children → 路由层 404）。
  - **为什么不再是“父链”**：锚点仅章后（§14.7），父链上**至多含一个章**，兄弟章的 Delta 不可见 → 跨章累积不可表达。先前“能累积”仅靠**卷级锚点**（卷是所有章的祖先）这一逃生口，而它在收窄中被关闭。章序前缀与 `current_position`、伏笔健康指标、孤儿诊断的「写作进度」口径**同源**。
  - **代价（已知并接受）**：`appliedDeltas` 随进度增长（前面所有章的 Delta 都在列表里，依赖现有截断机制）；`move` 章/卷会改变累积范围（合理——改了阅读序就该变）。
  - **章序的定义**：`deriveChapterOrder` 产出的是**先序文件位置序**（含软删章——编号不因删除而重排，保证已有 Delta / `expected_resolve_node_id` 的章号引用稳定）；**可见性由消费方处理**：节点级 `chapterOf` 对软删节点返回 `null`，「当前章」的退化分支必须取**最后一个未软删章**（否则删掉尾部章节会虚报写作进度一章，连带 Hook age/dormancy 与孤儿诊断基准偏移）。
  - **UI 展示编号 ≠ 本节的章序（2026-09）**：大纲页显示的「第N章」是 client 从整树推导的**纯展示编号**（只计未软删节点 ⇒ 删章后重排），**不参与任何计算**；本节 `deriveChapterOrder` 的章序含软删章、保引用稳定，是 Delta / 伏笔 / 写作进度的唯一口径。**两者不同源，不要互为替代**（想让 UI 改用服务端章序或反过来之前，先读本条）。
- `op=update` 应用时校验当前值等于 `from`；**不匹配则跳过该 change 并在 `conflicts` 中标注**（`{ field, expected, actual, deltaId }`），不返回 409——手动编辑实体 data 不产生 Delta 属正常行为，旧 Delta 的 from 与实际值断裂不是异常。
- `plot_edge` 连线不参与状态计算。
- **锚点仅章（2026-09）**：Delta 的触发节点只能是 `chapter`（写入侧 400/工具层拒绝）——卷太粗、场景太碎，一章一个状态变化点才是叙事现实；**收窄只限写入**，`computeState` 的 `at_node_id` 不限层级（「第 3 章第 2 场时他什么状态」是合法查询；**该宽松只给 API/工具层**——状态按章序前缀累积，非章节点只是某章的别名（场景→所属章、卷→该卷末章、root→初始值），因此前端两个选择器只列章）。
8. **`hook.data.expected_resolve_node_id`（预计回收节点）三层口径**：UI 只列章（两处渲染器同 helper）、数据层接受任意节点、分析层容忍非章（无章号 → `ready_to_resolve = null`，不猜测）。它与**伏笔关系源端**（`plants`/`advances`/`resolves` 硬校验章、服务端 400）不是同一层——别把两者收窄成同一个规则。代价已接受：事件粒度从场景退到章。
- **字段路径（2026-09）**：`field` 可为点分嵌套路径（`ability_panel.火系.等级`）——逐层下钻定位；**嵌套路径仅标量 `set`/`update`**，`add`/`remove`（数组语义）只在顶层字段——避免「数组语义 × 嵌套路径」的组合爆炸。解析口径见 `../db/schema.md`（数组段按同层 `name` 匹配取先序第一个；名字含 `.` → 不可寻址，记冲突不静默）。
- **物化事实字段不用 CAS（2026-09 裁决 a）**：hook 的 `data.status` 由写路径同步为最新值（终态守卫/列表/分组/AI 统计四处直接读它），与「`data` 保持初始值」的 `update` 前提**互斥** → 伏笔状态转移的 Delta 一律用 `op=set`（不声明 `from`），from→to 的叙事留在 `description`。**已知边界**：`at_node` 在首次转移**之前**的窗口返回最新值（基座即 `data`）——目标节点按其**所属章的进度章**判定，故该章之前的场景同属此窗口；接受此近似。
- **AI 推演是只读路径计算 + 提案生成器**：推演产生的状态变化**不落库、不进入主状态**，只以提案形式呈现，用户确认后由 executor 写入 `delta_records` 成为事实。推演与事实分离，防止 AI 假设污染创作数据。

## 5. 原子写

`outline.json`（及 `project.json`、AGENTS.md）保存必须走「写临时文件 → fsync → rename 覆盖」的**原子写**，禁止直接覆盖写。大纲是核心创作资产，原子写保证任意时刻磁盘上要么是旧文件要么是新文件（崩溃/断电不损坏）。

## 6. 软删 + 回收站

- 实体/关系/Delta 标 `deleted_at`、大纲节点标 `deleted`，**级联一并软删**（purge 才物理清除）；常规查询默认过滤，回收站 API 是访问软删对象的唯一入口；restore 级联还原。
- **手动删关系 = 物理删**（关系轻量可重建，不进回收站）。
- **可见性联动端点状态**：关系/Delta 的常规查询校验其端点（source/target、触发节点/目标实体）均未软删——任一端点软删即不可见；restore 级联还原全部关联，端点还原后自动可见（数据永不丢失，也不出现指向回收站对象的「幽灵关系」）。
- **restore 父链约束**：还原大纲节点时校验祖先链，存在软删祖先返回 409 `OUTLINE_ANCESTOR_DELETED`（提示先还原祖先），杜绝「可见节点挂在不可见父」的畸形树。
- **软删/还原更新 `updated_at`**（与常规编辑一致），保证提案快照比对语义统一——删除/还原后基于旧快照的提案必然 `PROPOSAL_STALE`。
- **块文档随 owner 生存**：章节点被软删 ⇒ 其 `document_records` 行保留但不可见（章还原即原样回来）；purge 物理删 = 一并删文档行。参考资料同款（实体软删/还原/purge 与通用实体一致）。**文档行不单独进回收站**：它没有独立生命周期，可恢复性完全由 owner 的软删/还原提供。

**为什么**：创作场景误删成本高，软删为还原留余地；关系与 Delta 随本体一并软删避免悬挂引用；可见性联动保证「还原必可见、可见必有效」。

## 7. Schema 演进：user_version 三态分流

以 data.db 的 `PRAGMA user_version` 为准**三态分流**：

1. **匹配** → 正常打开；
2. **高于程序版本（未来版本）** → **拒绝打开**（`SchemaVersionError`，数据不动、无 .bak）——堵降级数据丢失（用户装新版后回退旧版程序，旧版打开高版本库会重建清零）；
3. **低于（旧版本）** → **有迁移路径则按序增量迁移**（`db/src/migrations/` 按 version 序执行、每迁移一事务、失败回滚、`runMigrations` 时间戳快照 `data.db.v{n}.{时间戳}.bak`）；**无迁移路径才删库重建兜底**（备份 `.bak` 含 data.db，重建同步重置 outline.json）。

`project.json`/`outline.json` 的 `schema_version` **只管 JSON 结构，不参与重建判定**。删库重建策略于正式发布终止（增量迁移机制替代）。

## 8. 大纲节点结构化信息（麦基《故事》字段集）

大纲节点长期只有 title/summary 自由文本，作者无法挂载结构化信息。outline.json 节点新增可选 `data` 字段（`Record<string, unknown>`），按层级 schema 校验：

- **scene**：`goal`（场景目标/欲望）、`conflict_levels`（麦基冲突三层次 `inner`/`personal`/`extra_personal` 多选）、`value_from`/`value_to`（开场/收场价值——「没有不转折的场景」）
- **chapter**：`reversal`（章末反转）、`climax_scene`（章高潮场景引用，可选）
- **volume**：`climax_scene`（幕高潮场景引用）、`inciting_scene`（激励事件落位，可选）

字段集**宁少勿多**（每层 1-3 字段），是 AI 做小说理论分析的结构化输入基础。关联（人物/地点/伏笔）仍走 `relation_records`，不在 data 中重复建模。

**不变式**：编辑 data **不自动生成 Delta**（手动编辑实体/节点 data 不产生变更记录属正常行为）；变更记录由「+ 新建变更」显式创建。

## 9. 时间轴：event + timepoint 实体化

时间序与结构序是**两种正交的叙事维度**——大纲树表达阅读/结构顺序，时间轴表达事件发生顺序（倒叙、多时间线只能靠独立事件序表达）。事件是第 5 种实体类型 `event`（id 前缀 `ev-`），复用实体体系（泛型 CRUD/回收站/软删/关系，零新增机制成本）。

**G2 修订（时间标签点实体化）**：时间标签从事件剥离为独立实体 **timepoint**（第 6 种实体，id 前缀 `tp-`，`name` = 时间标签文本可重命名）——「先定义时间点、再挂载事件」：

- **挂载 = 通用关系表**：`occurs_at` 关系（timepoint → event，**1:n**，一个事件至多挂一个时间点；事件无挂载 = 未挂载，列表末尾「未挂载」兜底区）。
- **双独立线性序**：`timepoint.sort_order` = 组间顺序（整组移动不动内部）；`event.sort_order` = 组内排序键（跨组拖拽即改挂载）。两组序完全正交，**拖拽 `sort_order` 为权威**，时间标签不解析不排序。
- 事件/时间点 data 不产生 Delta（同 §8 语义）。

## 10. 对话历史持久化（pi session 文件）

对话历史**不入库**：一 session 一个 JSONL 文件，落在**项目目录内** `sessions/`（版本/entry 结构/字段见 `docs/db/schema.md`）。

- **随书目录，但不随包**（2026-09 修订）：改名/移动目录天然携带会话（由目录归属直接表达，不依赖 data.db 的 `project_id`）；但**备份 / 导出 / 云端都不含它**——对话历史不跳机器（`sessions/` 是纯本地目录，体积不受控增长不入备份）。
- **恢复类操作不触碰**：restore / import / 云 pull 只覆盖三文件，本机会话目录不写不删（存量旧包内的 `sessions/**` 条目接受并忽略）。
- **格式归 pi**：v3 树状 entry（消息、压缩摘要、模型与思考强度变更等）；由 pi `SessionManager` 负责读写、坏行容忍与版本迁移。本仓只消费「会话列表 / 消息序列」两个投影。
- **思维链落盘**：assistant 消息的 thinking block（含签名）原样持久化，**不剥离**——回放需要（anthropic 族多轮工具调用必须带签名）。
- **旧格式不迁移**：v1 扁平行 + `sess_*` 命名的历史文件留在磁盘，但不被 pi 发现（无效 header）、不出现在列表、不可续聊。
- **不建索引文件**：会话列表扫目录聚合（避开「索引与文件两套事实」）；代价是会话多时开销线性增长，属本地单用户可接受量级。
- 上下文压缩与裁剪由 pi 承担（见 `30-agent-loop.md` §1），压缩摘要落盘为 compaction entry。

**不变式**：会话文件路径只能由「磁盘发现 + header id 映射」得到，**禁止用客户端传入值拼接路径**；删除会话 = 物理删文件（无回收站、无软删）。

## 11. 自动备份与恢复

备份是「恢复到备份时点」的版本管理（区别于导出 = 文件传输），**全部项目级（跟随书籍）**：

- **频率**：project.json `backup_frequency_minutes`（缺省 10；null/0 = 关闭；仅枚举 1/5/10/15/30/60）；服务运行期间按频率定时检查，**仅当三文件（outline.json / data.db / project.json）任一 mtime 晚于上次备份时刻才生成新备份**——**变更判定补查追加来源**：`data.db-wal` 伴生文件（WAL 模式下普通写事务只追加 `-wal`、主文件 mtime 不变，漏检即丢全部 data.db 写；wal 缺失视为无变更）——**块文档（正文/参考资料）的每次保存都会追加 `-wal`，因此正文编辑同样触发自动备份，无需额外探测**。`sessions/` 不参与（不进包）。无状态（上次备份时刻 = `.backups/` 最新备份时间戳）、无变更跳过、不产生垃圾备份。
- **存储与保留**：项目目录 `.backups/`（随书籍移动自然携带）；每项目保留最近 20 份，超出删除最旧。
- **命名（文件名为唯一事实来源，无状态）**：`<YYYYMMDD-HHmmssSSS>-<自动|手动>-<设备>[-<标签>]-人物N-设定N-章N.zip`：毫秒时间戳（本地时区；字典序 = 时间序，列表排序与保留策略都靠它，毫秒位保证同秒多次备份可区分）＋**类型段**（`自动` = 定时器与覆盖前快照；`手动` = 立即备份触发）＋**设备段**（必填：来源机器，缺省 = 简化 hostname，可在设置页改名；不得含 `-`）＋可选**用户标签**（1-30 字符）＋**尾部固定三段统计**（`人物N-设定N-章N` = 备份时点该项目的未软删存量；固定尾部使解析可从尾部倒切，标签里出现类似字样也不会歧义）。**写入 = 解析 = 唯一格式**（2026-09 收敛，见 `20-api-backup.md`「命名」）：早期开发期的三类旧命名（秒级 `<YYYYMMDD-HHmmss>.zip`、带名称无类型段、单字母 `m`/`a` 段）**不再解析**——磁盘上仍留着（不删、不动，与 v1 会话文件同款口径），但不出现在列表、不可恢复、不参与保留策略（保留策略本就不碰非本程序命名的文件）。
**升级兜底（不丢最新数据）**：打开项目时若 `.backups/` 里**有文件但没有一份可解析**（旧命名残留导致的形态）→ 立即生成一份新格式备份；自动备份频率开启时下一次 tick 也会补一份（变更判定对「无可解析备份」视为需要备份）。旧命名**不做重命名迁移**——旧份没有设备/统计信息，硬补会谎报（统计必须描述该备份的内容）。
- **名称规则**：trim 后 1-30 字符，禁路径分隔符/保留字符/控制字符/纯点，sanitize 收敛 shared `sanitizeBackupName` 纯函数（服务端唯一执行点）；名称只进文件名不进 zip 内容。
- **重命名**：`POST /backup/rename` 只改名称段（时间戳与 kind 保持，标签 = 来源语义固定）；name 空 = 清除名称段；目标已存在 → 409 `BACKUP_TARGET_EXISTS`（杜绝静默覆盖）；文件名必须已是唯一格式（旧命名不参与列表 ⇒ 也无从改名）。
- **加载/导入以 project_id 为唯一 key**：zip 内 id 匹配书架 → **覆盖恢复（必须保留当前项目 id**——id 是书的身份，会话已随目录走、不再依赖它）；不匹配 → 导入新书（同名不同 id 不再 409，目录自动去重 `书名 (N)`）。**覆盖前服务端自动将当前状态打包为快照**（误操作永远有后悔药）；restore 的 data.db 校验与 import 同款（user_version 三态分流，绝不静默重建）。
- **重命名书名**：`POST /project/rename` 原子移动目录 + 更新 name，当前打开项目同步内部路径引用；会话按 id 不受影响；**启用云存档时同步 `MOVE` 云端书目录**（云端定位按 `project.id`，不按书名）。
- **云端副本（可选，2026-09）**：备份 zip 可推送到用户自己的云盘（WebDAV）——异地副本 + 多设备续写的可选通道，**不是事实源**（建到本地优先之上）。**拉取与本地 restore 是两种语义，不可混用**：本地 restore = 「回到那个时间点」；云端 pull = 「把另一台机器的东西拿过来」——**两者当下都只覆盖三文件，都不碰 `sessions/`**（会话不跨机器搬运；原先的会话并集已取消）。**块文档（正文/参考资料）随 data.db 走覆盖语义**：与大纲、实体、Delta 完全同款（2026-09 修订：原先随目录并集的 `references/` 已废弃）。**新机器恢复**：列云端书 + 导入为新书（`GET /cloud/remote-books` / `POST /cloud/import-book`，导入时就把同步状态写成「已同步」）。

**为什么**：备份粒度到书（书架是创作根的目录集合）；「有变更才备份」避免闲置期垃圾备份；文件名编码类型/名称/设备/规模保持无状态（无索引文件、无脏数据）；覆盖前自动快照把误操作风险降至最低（数据安全即「数据主权归用户」承诺的延伸）；云端存档作为**可选的异地副本**补上本地磁盘解决不了的两个缺口（磁盘损坏、多设备续写），但绝不进入事实源位置，也不需要任何自建后端。

## 12. 设定层级与分类

- **层级 = `belongs_to` 关系（setting → setting）**：子设定 belongs_to 父设定（「子属于父」，与「人物→设定所属」方向语义自洽）；`data.parent_id` 废弃（不再读写，`.passthrough()` 容错旧残留）。读写走 `relation_records` 索引，数量级优于扫 data JSON。**创建关系时服务端校验**：禁自指、防环（新父沿祖先链向上不得经过该子设定），违规 400 `VALIDATION_ERROR`；防环校验用层级邻接表（全量边构建 `child→parent` Map，写后失效惰性重建）。
- **分类统一 `data.tags: string[]` 标签**（前后端同名，UI 显示「标签」）；`data.category` 与旧 `rules` 分类语义废弃（004 迁移把旧 rules 分类值复制到 data.tags；`rules` 恢复「规则条款」语义仅设定详情页编辑）。标签筛选走服务端 `matchDataFilters.tags` 管道。
- **列表递归子树筛选**：`GET /api/v1/entity/setting?parent_id=` 匹配「直接或间接属于该上级」的递归子树（**不含上级自身**）——复用层级边结构 DFS 收集后代（防环守卫），服务端 JS 过滤路径（分页为服务端权威，客户端只过滤当前页会破坏分页）；与搜索/标签/排序/分页组合（AND）。

**为什么**：一处语义一处存储（关系表有索引、有端点校验、有回收站级联，层级天然复用）；分类与标签是同一语义的两套表达（YAGNI 取一）——标签是数组、天然支持多选分类与既有筛选管道。

## 13. 正文的读写边界（2026-09 修订，取代「正文不进系统」）

**正文进系统，但只进一条受控通道**：章级块文档由作者在本应用内书写，真相存 `document_records`（`owner_kind='chapter'`，键 = 章节点 id）。三条不可违背的边界：

| 边界 | 口径 |
| :--- | :--- |
| **仅在章** | 正文只挂 `chapter` 节点（卷/场景无正文入口，REST 层校验节点类型）；与 `current_position`、Delta 锚点、伏笔锚点的「章级三件套」同口径 |
| **AI 只读** | 工具面**不存在任何文档写工具**；AI 读取走独立只读工具（单章分页拉取）或聚焦章的节选注入。落笔永远由作者完成 |
| **编辑无副作用** | 保存正文**不产生 Delta、不自动推进 `current_position`**、不进关系表（与「手动编辑实体 data 不产生 Delta」同款：正文是内容，不是状态事实） |

**存储形态**：块编辑器的原生 JSON（块数组）为真相，另存 server 派生的**纯文本投影**（`content_text`，轻量 md：保块级结构、弃行内样式）——它同时服务 AI 读取、列表摘要、搜索与字数统计。**派生只能由服务端做**（唯一写入人），且失败不得阻断保存（最坏退化为尽力抽取的文本）。

**为什么不落文件**（2026-09 决策，取代早先的 `manuscript/` 目录方案）：块编辑器原生格式与 markdown 之间的互转是**双向有损**的（颜色/对齐/嵌套/媒体在 md 中无对应表达），若以 md 文件为真相源，每次「打开→保存」都存在静默丢结构的路径；而把它收进 `data.db` 后，备份、导出、云端、回收站、软删级联全部自动继承既有管道，工程上是净简化。**代价（已知并接受）**：正文不再是磁盘上可被外部编辑器打开的文件——外部编辑能力改为**导入/导出**（单文件 md / 块 JSON），且导出为 md 时**必须提示有损**。

**可读性**：`content_text` 让「已写/未写」「字数」这类派生信息无需原文即可回答（列表与大纲展示用），但它**不是**第二份真相——任何写路径都只写块 JSON，投影由服务端重算。

**为什么**：本地优先与数据主权的要求是「数据可导出、不被平台锁定」，不是「每个字都必须是裸文件」——块的 JSON 文档 + 一键导出 md/JSON + 完整备份 zip 已经满足可迁移性；而强行 md 化会把「编辑器能力」和「格式保真」做成互斥选择（md 真源下的完整论证见 `backlog.md` 的「块文档格式选型」条目）。

## 14. 人物数据分层与能力面板（2026-09）

人物页是「人物工作台」（master-detail），它的数据按**可变性三分**——这个分层不是 UI 分组，而是三条硬契约的共同依据：**双视图语义**（UI 文案：人物档案 / 阅读进度）、**变更记录字段白名单**、**AI 提案边界**。字段清单见 `../db/schema.md`「人物 data 分层」。

### 不变式

1. **不可变字段不参与 Delta**：姓名（`entities.name` 列）、角色定位 `role`、描述 `description`、角色优先级 `priority`（**作者视角的档位分类**——谁是主角是作者的判断，不随阅读进度变化；它是人物列表默认排序档的依据，见 `../db/schema.md`「人物 data 分层」）。原因不只是口味：`name` 是**表列**，关系展示（`sourceName`/`targetName`）、列表行、AI 检索全部读它——若允许 Delta 改 name，`computeState` 会算出"另一个名字"，而全系统其他角落仍显示原名，**同一人物两个名字且无处报错**。`role` 同理（列表摘要与 AI 摘要在用）。人工仍可经 `PUT` 直接编辑三者（改名是创作常态）。**已知边界（待收口）**：该约束现已在**前端**（下拉白名单 + 阅读进度 tab 只读展示）与 **AI 提案层**（`propose_add_delta` 按 shared `IMMUTABLE_FIELDS.character` 拒绝该层字段：`role` / `description` / `priority`）生效；**REST 保持泛型**（直连 API 仍可写——与 S13.3 分层一致）。
2. **双视图必然一致**：不可变字段不出现在变更记录字段下拉 → 两个视图里它们**必然相同**，变化只出现在可变字段——这是「人物档案 / 阅读进度」两个 tab 不出现语义裂缝的前提。
3. **只有「人物档案」视图可编辑**：`data` 是初始值；「阅读进度」视图是 `computeState(at_node = current_position)` 的计算结果，只读——要改当前状态就必须建变更记录（否则用户以为在改"当前状态"、实际改了初始值，静默错误）。
4. **能力面板结构与值分工**：增删/改名/排序节点 = 人工编辑（不产生 Delta）；**只有已存在的叶子可被 Delta 修改**（路径 = `ability_panel.<分组>.<叶子>`）。这样"结构漂移"永远不会让旧 Delta 失效。
5. **叶子值类型 = `string | number`**（对齐 `DeltaChange` 同域）：要"等级 + 熟练度"就拆两个叶子——不搞对象叶子（对象无法表达局部更新的 Delta，复杂度爆炸）。
6. **模板派生 = 结构快照深拷贝**：内置常量模板 / 从已有角色复制结构；派生后改源角色**不影响**已派生角色（引用联动需要模板版本 + 已派生结构迁移，直接炸掉复杂度）。模板里的 `value` 视为默认值（派生后成为该角色的初始值）。
7. **章级锚点三件套**：`current_position`、变更记录锚点、伏笔锚点（`plants`/`advances`/`resolves`）**均只支持章**——卷/场景既不要变更记录也不要伏笔标记。同一章的三种锚点语义一致：**写到哪一章 / 那一章发生了什么变化 / 那一章埋了什么伏笔**。

### 为什么这么切（而不是一套扁平字段）

- 「写到后面忘了前面」是长篇核心痛点，而大量 AI 分析与 UI 展示需要区分"这个人的固定设定"与"写到第 N 章时的状态"——不分层时两者只能靠约定，约定一漂移就出现"初始化视图显示的名字与关系网里的对不上"。
- 能力面板（类似游戏/系统流角色面板）的处境关键：它是**会被 Delta 推动的可变数据**（等级 3 → 5），所以必须能走嵌套路径累积；但它的**结构是用户自由定义的**，所以结构变化不能进 Delta（无意义且不可表达）。两条约束共同推出「结构人工、叶子可 Delta」这一分区。
- 面板模板不做成新实体/新表（YAGNI）：「从已有角色复制结构」已覆盖主要场景（同门派/同体系角色结构相同）；真需要模板库时，把派生函数的"源"从角色记录换成模板记录即可，零返工。

## 15. 推演节点标记（2026-09）

「剧情推演」的输入是**作者标定的推演边界**：作者在大纲树上把若干**章**标为「推演节点」，再让 AI 在这些标记上做开放式发散（单标记）或剧情线探讨（多标记）。标记是**作者意图的记录**，不是剧情数据——这条定性决定了下面全部不变式。

**存储**：`project.json` 的 `deduction_nodes: string[]`（节点 id 数组；字段契约见 `../db/schema.md`）。与 `current_position` 同类——**页面级标记**，随三文件自动走备份 / 导出 / 云端 / 恢复，无需任何额外管道。

### 不变式

1. **仅章**（写入侧 `PUT /project/config` 校验）：与「章级锚点三件套」（`current_position` / Delta 锚点 / 伏笔锚点）同口径。卷太粗（区间内任何推演都对得上）、场景太碎（区间跨度会混层级）。放宽成本低——只改写入侧校验（读侧本就泛型）。写入校验按**可见性**判定（自身与祖先链均未软删）——祖先软删的章不可达 ⇒ 400，不做静默丢弃；读侧对存量标记仍按过滤口径处理。
2. **顺序 = 树序，不是标记先后**：数组存的是**集合**，顺序由**可见章先序**推导（shared 纯函数 `orderVisibleChapters` 是唯一编号口径：UI 徽标、注入文本、AI 工具三处同源）。⇒ 增删标记、拖拽改树序后编号自动重排，不需要任何重排 UI，也不可能出现「两个起点」这类非法状态。
3. **角色文案是派生物，不落库**：单标记 = `推演节点`（唯一锚点 ⇒ 开放式发散）；多标记 = 首位 `推演起点`、末位 `推演终点`、中间 `推演节点 k`（k = 树序位置）。库里只有 id，文案随数量与树序自动重算。
4. **不产生任何状态副作用**：标记不产生 Delta、不推进 `current_position`、不进关系表——它是作者意图而非剧情事实（同 §8「编辑 data 不自动生成 Delta」）。
5. **AI 只读**：工具面只有查询（`get_deduction_marks`），**没有任何改标记的提案或执行工具**——推演边界是作者的判断。推演结论本身也不落库：AI 只出提案，作者确认后由 executor 写 `delta_records` / 大纲 / 关系（同 §4「AI 推演是只读路径计算 + 提案生成器」）。
6. **读侧过滤，不自动清理**：软删章与已 purge 的 id 在**渲染、注入、工具**三处一律过滤；**不写清理任务**——软删可还原（标记自动回来），purge 后 id 永久失效而用户下次增删标记时的**全量写入**自然收敛。

**为什么存 `project.json` 而不是节点 `data`**：① 节点 `data` 的语义是麦基结构化字段集（§8），塞 UI 标记会稀释它；② 标记是**集合**语义（起点/终点由相对位置定义），散进每棵子树后「谁是起点」要全树扫描才知道；③ `data` 是部分合并、**删不掉键**，取消标记只能留 `false` 残留；④ 写 `data` 会刷新节点 `updated_at`，让在途提案无谓失效。代价（已知并接受）：标记不随节点走——换书当然也不该跟。

**两个消费面**（契约见 `../api/80-api-chat.md` 与 `../api/tool-calling.md`）：悬浮「问 AI」注入**标记集合**（客户端只发布尔标记，服务端现读 `project.json` 展开，客户端过期/伪造 id 不进来）；AI 侧由 `get_deduction_marks` 按需拉取标记与相邻区间骨架。
