# 拆解小说（导入式批量管线）详细设计

> **本文档职责**：回答「拆解为什么不是 chat 工具、五阶段各归谁、批怎么分、长文本怎么进上下文、归并错并怎么办、中断了怎么续」——阶段职责、调度口径、幂等与不变式。
> 端点契约见 [`../api/120-api-decompose.md`](../api/120-api-decompose.md)；数据表见 [`../db/schema.md`](../db/schema.md)（`decompose_jobs` / `decompose_batches`）；视觉与页面结构见 [`../ui/DESIGN.md`](../ui/DESIGN.md) §拆解小说；上下文预算见 [`20-context.md`](./20-context.md)；工具契约见 [`../api/tool-calling.md`](../api/tool-calling.md)；数据模型见 [`10-data-model.md`](./10-data-model.md)。

## 1. 定位与边界

**拆解小说** = 用户提供一份既有小说文本（`.txt`）→ 建项目 → 由 LLM 把它整理成结构化创作数据（大纲 + 章正文 + 人物/设定/地点/关系 + 拆解报告）。

它是**一条独立的导入式批量管线**，不是 chat 工具集的一部分。三条硬约束，缺一条这个结论都不成立：

| 约束 | 事实 | 结论 |
| :--- | :--- | :--- |
| 写路径 | 执行类工具不注册 registry；`propose_*` 逐条提案 + 用户确认，提案仅内存、TTL 与条数上限封顶 | 一本数十章小说的产出是数百条写入 ⇒ 逐条点击不可行、也不可断点累积 |
| 长任务 | chat 是单项目单在途流（`CHAT_BUSY`），SSE 断开即全链路 `abort()` | 数十分钟到小时级的任务不能挂在对话流上 |
| 文档写权限 | 工具面**不存在**任何正文/文档写工具（结构性禁止） | 原文入库必须走非 AI 路径 |

**边界（不可回退）**：

- **模型仍然没有任何写工具**。模型只产出结构化 JSON；落库全部由服务端确定性代码 + schema 校验完成。「点开始拆解」= 用户对整批导入的**一次性授权**（与「导入备份」同类），不是 AI 越权。
- **不走提案仓**：提案是毫秒级交互对象（仅内存 / TTL / 条数上限 / 绑项目）；拆解是长任务，结果由用户事后核查 + 单批重跑修正（§7）。
- **不改产品定位**：AI 仍不生成正文——原文来自用户文件，不是模型产出（见 `00-master-design.md`）。
- **两类入口**：① **首次拆解** = 「基于小说文件创建项目」（S0 切分 → S1 建档）；② **续拆** = 同一项目内开**新 job** 接着拆还没拆的章（§7.1）——**不要求重传源文件**（S1 是正文全量导入，全章已在库）。不做「把已有小说拆进另一本书」。撤销路径 = 删书（`POST /project/delete`，有同步记录时先推一份上云）或恢复拆解前的自动备份 zip（打开项目时的兜底备份已生成）。建档时在 `project.json` 写 **`origin: "decompose"`**（书架分「小说拆解」组的唯一依据；出处标记与实体的来源列是两回事，**后者仍不引入**——不给 `entities.data` 加来源字段）。
- **正文全量导入不受拆解范围限制**（§4）：范围只约束 LLM 分析，用户即使只拆前 N 章，也能在系统里通读全文。

## 2. 五阶段

| 阶段 | 做什么 | 产物 | 是否调用 LLM |
| :--- | :--- | :--- | :--- |
| **S0 解析** | 编码探测 → 文本归一化 → 章节切分（§3）→ 预览确认 | 预览（章列表 + 统计 + 警告）；**不落库** | 否 |
| **S1 建档** | 创建项目 → 大纲（卷/章）→ 逐章导入正文 → 落批规划 | `outline.json` + `document_records` + `decompose_batches` 行（`pending`） | 否 |
| **S2 逐章抽取** | 按批调 LLM，产出「章摘要 + 人物/设定/地点/关系线索」 | 每批结果写入 `decompose_batches.result`（**只暂存，不落业务表**） | 是（批数次） |
| **S3 归并** | 规则层去重 + 一次别名归并调用 → 写入实体/关系 + 章摘要回写大纲 | `entities` / `relation_records` / `outline.summary`；写入清单进 `decompose_jobs.merge_written` | 是（1 次） |
| **S4 报告** | 用章摘要做全书聚合 → 写拆解报告 | 一条 `entities(reference)` + 其块文档 | 是（1 次） |

**S2 与 S3 必须解耦**（先暂存后统一归并，不做「边抽边写」）：① 归并是**全局任务**（别名聚类需要看到全书的提及才能定实体边界），逐批写入会让实体边界被前几批锁死；② S2 失败重跑零副作用（没写业务表）；③ 归并规则改进后**不用重付 LLM 成本**就能重跑 S3。

**总调用数 = 批数 + 1（归并）+ 1（报告）**。

**续拆的阶段差异**：续拆只有 **S1'（落 job 与批规划，不建大纲、不导正文）+ S2 / S3 / S4**——S0 与正文导入不参与（章已在库）。

### 2.1 模型调用形态：一律走 pi 的 Agent 路径 + 拆解会话落盘（2026-09 裁决）

**凡调 LLM 一律用 pi 的能力，不自建 provider 适配**（实现单点 = `server/src/decompose/llm.ts`）：

```
createAgentSessionServices({ noExtensions, noSkills, noPromptTemplates, noContextFiles, systemPrompt: 本次 system })
  → createAgentSessionFromServices({ noTools: "all" })
  → SessionManager.create(cwd, <项目根>/sessions, { id: "decompose-<jobId>" })
  → 每 turn 前 sessionManager.resetLeaf() → session.prompt(用户消息) → 取末条 assistant 文本
```

**为什么不能直连 `ModelRuntime.completeSimple`**（早期实现踩过的坑）：provider 特化行为、重试/超时设置、思考档位**只在 pi 的 Agent 包装层生效**（`pi-coding-agent` 的 `core/sdk.js` streamFn → `transformHeaders` → `mergeProviderAttributionHeaders`）。实测：opencode 系 provider 缺 `x-opencode-session` 直接 `400 MissingSessionID`（直连必失败、走 Agent 路径必成功）；自己补头/补重试等于**无限期跟随上游**。

**会话形态 = 每 job 1 + N 枚落盘会话（主会话 + 每段 worker），每批一个 turn、每 turn 独立成根**：

| 口径 | 值 | 理由 |
| :--- | :--- | :--- |
| 会话数 | **每 job 1 + N 枚**：主会话（计划留档 + 汇总 + S3 归并 + S4 报告）+ 每段一枚 worker 会话（各写本段批次） | 分段并发（§2.2）；主会话保住「一次拆解 = 一个入口」的审计锚点，worker 保住每批完整回放 |
| 落点 | `<项目根>/sessions/`（**根目录**，与 chat 会话同目录）；pi 的落盘文件名为 `<时间戳>_<会话 id>.jsonl`（命名由 pi 生成，本仓不自造） | chat 面板可见；**纯本地目录、不进任何 zip**（备份/导出/云端都不含会话，新机器不回放拆解过程记录） |
| 会话 id | 主 `decompose-<jobId>`；worker `decompose-<jobId>-w<k>`（主 id 经同一清洗函数组装，`-w<k>` 后缀追加在清洗结果之后） | 前缀即 kind（零成本判别）；**判定与查找一律用会话 id**（文件名带时间戳前缀，不得用文件名 glob）；provider 侧会话身份/缓存键稳定 |
| 每批 turn | prompt 前 `resetLeaf()` ⇒ **新根** | 上下文只含本轮（累积历史是 O(N²) 重复付费，见下表） |
| 自动压缩 | `setAutoCompactionEnabled(false)` | 一轮一上下文，没有可压缩的东西 |
| 工具 | `noTools: "all"` | 拆解只需模型产出 JSON；**正文由服务端注入，不需要工具来读**（§4.1） |
| 资源 | 四项全关 + 本次 system prompt | 不注入 pi 内核提示词、**不注入项目 AGENTS.md**（拆解提示词自包含） |
| 环境块 | 接受 pi 追加的 `Current working directory` | pi 的 prompt builder 行为（`core/system-prompt.js`），不自己裁剪 |
| 记录格式 | 真实 user / assistant 消息（含本批原文）+ `appendCustomEntry("decompose", …)` 过程条目 | 前者 = 完整回放（chat 面板）；后者 = 结构化时间线（`#/decompose` 读，**不参与 LLM 上下文**） |
| 会话名 | 主 `《书名》拆解`；worker `《书名》拆解 · 段 k/N` | 列表里显示正经名字，而不是被截断的原文 |
| chat 侧 | **只读**：`POST /chat` 拒 `decompose-*`；会话可见、可删；有在途 job 时禁删 | 拆解会话的历史不是给聊的（拿一整本原文当上下文续聊，费用与语义都错） |
| 保留 | 保留 `DECOMPOSE_KEPT_SESSIONS` **个 job 的全部**拆解会话（主 + worker 合计），超出删最旧 job 的全部（§7.2） | 每轮一份原文副本，不能无限长；job 内多枚不额外占额度 |
| 取消 | 不 abort 在飞调用 | 与 §7「每段当前批跑完即停」一致（在途 ≤ N，结果不浪费） |

**为什么每批新根、不用一条连续历史**（粗算一本 2.12M 字 / 757 章 ≈ 177 批 / 每批 12k 字）：

| 做法 | 每轮输入 | 全书累计输入 |
| :--- | :--- | :--- |
| **新根**（本口径） | 本轮 12k 字 + 快照 ≈ 9k tok | ≈ **1.6M tok** |
| 累积历史 | 前 k-1 批原文 + 本轮 | ≈ **1.2 亿 tok**（O(N²)，旧批被反复重发） |
| 累积 + 自动压缩 | 压缩摘要 + 最近若干轮 | 少一些，但压缩自身要额外调用、摘要会漂移 |

**提示缓存不改变结论**：缓存键是**会话 id**（pi 从 `sessionManager.getSessionId()` 取，两种方案一致），差别只在「每轮前缀是否与上一轮相同」。新根下只有几百字的 system 段可能命中（且常低于 provider 的最小可缓存长度），但**每轮输入本来就是新内容，命中率低不是损失**；累积那种「高命中率」是在给一份本就贵 80 倍的输入付更低单价（按 90% 命中、0.1x 折算后仍贵 ≈15 倍）。

### 2.2 分段并发（2026-09 裁决）

**墙钟的主导项是串行解码**：每批延迟 ≈ 模型思考 + 输出解码（样本书实测 ~80s/批），而总输出 ∝ 章数 ⇒ 串行墙钟 ≈ 总输出 ÷ 解码速度，**与批大小无关**（批大小只影响每批固定开销）。所以数量级提速的唯一杠杆是并发——做法是「分段并发」，不是「N 个独立 job」：

| 口径 | 内容 |
| :--- | :--- |
| 段 | 沿批边界把批序切成 `min(并发数, 批数)` 段、按累计字数均衡（纯函数，确定性；章不切开的口径不变） |
| 执行 | **段内串行、段间并行**；每段一枚 worker 会话 + 一份独立滚动累积（§4.1） |
| 段首 | 统一用 job 起始快照（库内实体 + 范围前 `DECOMPOSE_SNAPSHOT_PREV_CHAPTERS` 章摘要）——段间不共享本轮产物 |
| 段间一致性 | 与「续拆」同源：跨段一律交 S3 全局归并（同名合并 + 人物别名归并 + 悬空过滤），不做段间同步 |
| 并发数 | 创作根配置 `decompose.concurrency`（缺省 / 钳制见代码常量）；**建 job 时快照进 `decompose_jobs.concurrency`**，resume / 重跑按快照重算段（改配置只影响新 job） |
| 在途上限 | 同时最多 N 个批在飞；「停止 / 切书」= 每段跑完当前批即停（不 abort 在飞调用） |
| 限流 | 批级重试（≤ `DECOMPOSE_BATCH_MAX_ATTEMPTS`）不变；并发布补 429 / 限流指数退避 + 抖动（参数与实现单点见代码；后台任务慢比失败好） |
| 时间线 | `GET /decompose/job/log` 合并主会话与各 worker 会话的过程条目（按时间排序）；`batch_start` 条目带段号 |

**为什么不是 N 个独立 job**：job 是「一项目一活跃任务 + 单区间范围 + 一次 S3/S4 收口」的语义单元（§7.1）；N 个 job 会撞互斥、把归并拆成 N 次、并让「已拆章并集」口径错乱。段是 job 内部的执行细节，不是业务单元。

## 3. 章节切分

四层，逐层可验证。**候选模式表与全部阈值的单一定义在代码**（`server` 的拆解模块），本节只写口径与「为什么」。

### 3.1 归一化

1. **字节层**：BOM 探测（UTF-8 / UTF-16LE / UTF-16BE）→ **严格 UTF-8 解码** → 失败回退 **GB18030**。实测：一份样本是 UTF-8-BOM、另一份是 GB18030（`file` 判为 ISO-8859，按 UTF-8 直读必乱码）。`TextDecoder` 原生支持这些编码，不引入依赖。
2. **文本层**：换行归一（`\r\n` / `\r` / `NEL` / `U+2028` / `U+2029` → `\n`，实测有样本用 NEL 分行）、去 BOM、行尾空白清理。

**解码永不抛错**（`TextDecoder` 非致命 + GB18030 回退）⇒ 二进制文件会被解成乱码文本并按 §3.4 退化路径等分，**不做魔数嗅探**（有意）：`DECOMPOSE_FILE_INVALID` 只覆盖「归一化后无文本」。

**解码在服务端**（客户端 POST 原始字节）：切分带校验与修复层，预览与 job 必须共用同一份实现——客户端解码会立刻变成两份逻辑。体积上限 = `DECOMPOSE_MAX_FILE_BYTES`。

**源文件不落盘**：`analyze` / `start` 只吃内存字节，服务端不留临时文件；S1 把**全量**正文（不受 scope 限制）写成章块文档，切片含标题行、归一化只改行尾空白与换行 ⇒ **项目内章正文 = 源文本的规范化全量副本**，因此续拆不需要源文件，也不需要把原件复制进项目目录。

### 3.2 候选扫描

逐行扫描，**只考虑 `strip()` 后长度 ≤ `SPLIT_TITLE_MAX_CHARS` 的行**。模式表按优先级：章/回/节 → 卷 → 前置关键词（序章/楔子/前言/引子/尾声/后记/番外/外传/附录…）→ 英文章节。

**实测校准（两份真实样本，结论与社区通行做法相反的部分）**：

| 社区常见规则 | 实测反证 | 我们的取舍 |
| :--- | :--- | :--- |
| 标题以标点结尾 → 丢弃 | 一份样本 765 个候选行里 **232 个**合法标题以 `！？（）` 结尾，另有 1 个含 `。` | **不加标点护栏**，只保留长度护栏 |
| 数字编号式（`1. 标题`） | 命中全是正文列表项（`1，同行者：…`），0 真阳 | **明确排除**，并把理由写进注释防后人"顺手加上" |
| 全角空格缩进 = 正文段落 | 另一份样本 **98.7% 的非空行**以全角空格开头（正文普遍缩进），且 8 个章标记行本身带全角缩进 | **不引入缩进判据**，改用 §3.3 的相邻重复合并 |
| 长度上限（35–80 字） | 两份样本 `> 40 字` 的候选 **= 0**，标题最长 28 字 | 采用，阈值 = `SPLIT_TITLE_MAX_CHARS` |

另采纳社区的**排除规则**（「第三部分 / 第三节课 / 第三部队」这类计数词歧义命中即丢弃）与**卷优先**（同一行既匹配卷又匹配章时按卷处理）。

**已知限制（罕见形态）**：同一行既含卷又含章标记时只发卷切点，该行的章切点被吞（其后续文本归入前一章）；卷标题也会带上未剥离的章标记文本。升级路径（发两个切点 + 剥卷前缀）见 [`backlog.md`](./backlog.md)。

### 3.3 聚合校验与修复（算法本体）

1. **规则融合 + 结构性评分**：**主规则**（章/回/节、卷、英文）各自切一遍，按评分函数选最优；**关键词规则（序章/楔子/前言/尾声…）确定性并入胜者**，不参与评分。评分维度：序号连续性、长度均匀度、数量合理性、marker 一致性、覆盖率。**理由**：中文小说的计数词不固定（这本用「章」、那本用「回」），单条规则调参必然在某类书上翻车；而关键词候选量少，当成候选集整体评分时会拖低长度均匀度与 marker 一致性，导致「不加关键词」反而胜出、序章/尾声丢切点。评分函数是纯函数、可单测。
2. **相邻重复合并**：相邻候选标题归一化后相同且间距 < `SPLIT_DUP_MERGE_CHARS` → 合并（取后者为起点）。实测 8 处：裸行标题紧跟缩进的同名行。
3. **卷首目录页启发式**（**必须排在微段修复之前**）：连续 ≥ `SPLIT_TOC_RUN_MIN` 个命中且每节正文 < `SPLIT_TOC_SEGMENT_CHARS` → 判为卷首目录页丢弃（两份样本未触发，但该形态真实存在；误判风险 = 极短章的书，预览里会显示「丢弃了 N 段作为目录页」）。**顺序理由**：目录条目本身短于 `SPLIT_MIN_SEGMENT_CHARS`，若排在微段修复之后会被当误命中逐个吃掉 ⇒ `TOC_DROPPED` 永不触发、假章节直接漏进大纲。
4. **微段修复**：间距 < `SPLIT_MIN_SEGMENT_CHARS` → 并入前一段；并入后仍过短 → 判该候选为误命中，丢弃。
5. **超长块回扫**：段长 > `SPLIT_LONG_BLOCK_FACTOR` × 中位数 → 用更宽松的规则（允许行内出现、允许任意缩进）回扫补漏标题。回扫无果时降级为预览里的「疑似合并章」提示，**不静默处理**。警告里的章号 = 该章在返回章列表里的 `index`（**同源，不另算编号**）。当前两份样本均不触发（早期一版 `三少爷的剑` 因源文件缺章标记而触发过）。
6. **编号校验只做提示**：统计非递增点（实现口径：样本 757 章里有 17 处重启——多部/副本各自编号；按候选行粗算会更高）→ 预览提示「检测到 N 处编号重启，疑似多卷」。**编号永不参与排序**：章序 = 文件位置序，与 `10-data-model.md` §4 的既有口径一致。
7. **卷判定**：卷标记数在 `[2, SPLIT_MAX_VOLUMES]` 区间 → 按卷分组；否则单卷「全书」（`root` 仅接纳卷、章只能挂卷，故单卷是必须的兜底）。
8. **前置块** → 「前言」章（实测一份含作者自述与来源行、另一份含简介与水印），**参与抽取**——成本可忽略，而作者自述有拆解价值。
9. **标题清洗**：去掉编号前缀与前导全角空格（大纲页已有「第N章」徽标，标题里再带编号会重复）；剥离后为空 → 保留原文行（如「第三十四章」）。

### 3.4 退化路径

候选数 < `SPLIT_MIN_CHAPTERS` 或密度校验失败（中位段长 < `SPLIT_MIN_SEGMENT_CHARS`）→ 判「无章节结构」，按段落边界等分（边界优先级：空行 > 换行），目标 `SPLIT_FALLBACK_TARGET_CHARS`，标题「第 N 部分」，预览明确标注「未检测到章节结构，已按字数等分」。

**章 `charCount` 是近似计数，不是切片长**（退化路径尤其明显：块计数不含空行分隔符）——**不得当偏移量用来裁文本**（会错位或丢字符）；消费方要裁文本必须自己重新按切片计算。正常路径同理：切片 trim 掉了分隔换行，故 `ΣcharCount < totalChars` 恒成立。

### 3.5 预览

`POST /decompose/analyze` 返回：编码探测结果、总字数、章数/卷数、字数分布（min / median / max）、**章列表（序号 + 标题 + 字数，全量返回）**、警告列表（编号重启 / 疑似合并章 / 目录页丢弃 / 退化等分）。警告码与消息文案的单一定义在服务端（`api/120-api-decompose.md` 的码表）；**微段修复不产警告**（它只丢切点不丢文本，合 §9 不变式 9 的「不静默」口径：文本始终在某一章里）。**实测参考（回归对照，两份真实样本）**：`三少爷的剑` = UTF-8-BOM / 253,629 字 / **48 章**（含前言）/ 1 卷 / 字数 min 1838 · median 5257 · max 6878 / **0 警告**；`从姑获鸟开始` = GB18030 / 2,123,725 字 / **757 章** / min 2005 · median 2545 · max 6162 / 警告 `DUPLICATE_MERGED` + `NUMBERING_RESTART`。两份均满足 `ΣcharCount < totalChars`（§3.4 口径）。**预览只读**——编辑切分（重命名/合并/拆分章）是另一个量级的功能，列入 `backlog.md`。**统计只展示 `totalChars`**：章字数和恒小于总字数（切片 trim 掉分隔换行），并排展示会让用户以为丢了字。

## 4. 批调度（S2）

| 口径 | 内容 |
| :--- | :--- |
| 组批 | **自适应**：目标 `DECOMPOSE_BATCH_TARGET_CHARS` 字/批，贪心装箱；单批章数 ≤ `DECOMPOSE_BATCH_MAX_CHAPTERS`；单章超目标字数 → 单独成批。**双向预算守卫**：按激活模型的 `contextWindow` / `maxTokens` 预检——估算输入（正文 + 每批固定开销 + 输出预留 + `DECOMPOSE_INPUT_SAFETY_TOKENS`）不超窗、输出（章数 × `DECOMPOSE_OUTPUT_TOKENS_PER_CHAPTER`）不超 `maxTokens`，超限按章拆批（章为最小单位，永不切开单章）；**单章自身超限**→ 保持单章成批，由执行期在**发调用之前**显式失败并给出明确文案（不落进 pi `clampMaxTokensToContext` 压输出的路径） |
| 对齐护栏 | 抽取 schema 强制「每章一个条目」；服务端校验批次覆盖的章集合齐全。缺章 → 整批重试（≤ `DECOMPOSE_BATCH_MAX_ATTEMPTS`）→ 仍失败标 `failed` 并**继续后续批**（不阻塞整个 job） |
| 并发 | **N 段并行、段内串行**（§2.2）；N 来自创作根配置、建 job 时快照。理由：串行墙钟 ≈ 总输出 ÷ 解码速度、与批大小无关 ⇒ 并发是唯一数量级杠杆；限流风险用退避兜 |
| 范围 | 起止章（默认全书）+ 开始前**预估**（批次数、调用次数、粗估 token/费用）。费率读 pi 模型目录的 `Model.cost`（`getModelRuntime()` 是唯一入口），**不自建定价表** |
| 项目数据快照 | 跨批 / 跨轮携带「已有名字 + 关系 + 前置章摘要」，两层来源、长度受控（§4.1）——**不是把前文原文带上** |
| 成本结构 | 输出 ∝ 章数（≈每章一条摘要 + 若干实体，费率是输入的 3–5 倍）；正文输入 ∝ 总字数；**批处理只省固定开销（系统提示 + 指令 + 快照），省不了输入与输出** ⇒ 真正的成本杠杆是「范围」 |

### 4.1 项目数据快照（上表「项目数据快照」的组成口径）

模型每轮拿到的「上文」= 两层，**不是把前文原文带上**：

| 层 | 来源 | 内容 |
| :--- | :--- | :--- |
| 起始快照 | job 开始时**读库一次**；**各段共用这一份** | 已有实体名（人物带 `role`，按 主角 → 主要配角 → … → 龙套 排序）、已有关系、**新范围前 `DECOMPOSE_SNAPSHOT_PREV_CHAPTERS` 章的摘要**（续拆的「前置连续性」） |
| 本轮累积 | **本段**已完成批 | 名字 / 关系 / 上一批摘要（段内滚动；段间不共享，跨段一致性交 S3） |

- **起始快照读库取全**：实体按 `MAX_ENTITY_LIST_LIMIT` **分页取完**（与 S3 同名复用同一实现）——只取一页会让提示词里的既有名字不完整，模型看不到的名字无法被复用（会重复建行）；关系读取本身不分页（单查询返回全部可见关系，不得另加 limit）。
- **预算** = `DECOMPOSE_SNAPSHOT_MAX_CHARS`；超预算丢弃顺序（先丢 → 后丢）：**设定 / 地点名 → 关系 → 前置摘要 → 人物名**（人物是关系端点的关键）。
- **丢弃必须显式告知**（如「（已省略 12 个设定 / 地点名）」）——静默截断会让模型以为自己看到了全部。
- **关系端点判据唯一在 S3**：S2 抽取层**不再**因「端点不在已知名字集合」丢弃关系（并发下这个集合本就不全，会把跨批 / 跨段关系误判成幻觉）；端点存在性只由 S3 悬空过滤（§6 第 1 层第 4 步）按**落库实体集合**判定。名字集合（含预算裁剪）只服务提示词渲染。
- **不注入拆解报告 / 全书摘要**：实测需要再加（`backlog.md`）。

## 5. 抽取 schema 口径

每批返回「逐章对齐」的 JSON：`chapters[] → { chapter_id, summary, characters[], settings[], locations[], relations[] }`。

| 字段 | 口径 |
| :--- | :--- |
| 章摘要 | ≤ `DECOMPOSE_CHAPTER_SUMMARY_MAX_CHARS` → 写入 `outline.json` 节点 `summary`（会被聚焦章注入使用，见 `20-context.md` §2） |
| `role` | 必填；提示词给建议词表（主角/主要配角/配角/反派/龙套），**服务端不校验**——契约本就是自由文本（`z.string().optional()`，UI 无枚举、无 role 筛选），不在管线里私造枚举 |
| `description` | 人物必填（人物契约的必填口径 = 前端表单 + AI 约定）；长度受 `DECOMPOSE_DESCRIPTION_MAX_CHARS` 约束 |
| `alias` | **单值**（`character.data.alias` 是 `z.string()`，存不下多别名）；其余别名进 `description` 的「（又称：X、Y）」 |
| `gender` / `age` / `race` | **只在文中明确时填**，不确定留空 |
| `personality[]` / `motivation` | 有则填；`personality` 限条数（`DECOMPOSE_PERSONALITY_MAX_ITEMS`）、`motivation` 限长度（`DECOMPOSE_MOTIVATION_MAX_CHARS`） |
| `setting.tags[]` / `setting.rules[]` | 短标签与短句（UI 把 `rules` 渲染成 tags 控件，长文本放进去会难看） |
| `location.type` | 自由文本；`parent_id` **不填**（不做地点层级） |
| `ability_panel` / `custom_fields` | **不填**——能力面板是用户自定义字段树，AI 建树会污染结构；拆出的武功体系一律进「设定」 |
| 关系 `type` | 收窄到 8 类：`ally` / `rival` / `mentor` / `family` / `kills` / `belongs_to` / `owns` / `masters`——**不给全 17 类**（否则会出现 `plants` / `occurs_at` 这类语义错的关系） |
| 每章条数上限 | 人物 / 设定 / 地点 / 关系**各自一个具名常量**（`DECOMPOSE_CHAPTER_MAX_CHARACTERS` / `_SETTINGS` / `_LOCATIONS` / `_RELATIONS`），超限服务端截断并记日志 |

**落库阈值（S3）**：人物与关系要求**跨章出现 ≥ `DECOMPOSE_MENTION_MIN_CHAPTERS` 章**（单章出现的路人/一次性互动只进报告）——这是压噪音的主闸门；设定与地点**不设阈值**（一次出现也可能是重要宝物/剑法），靠提示词约束「只抽对剧情有影响的」。

## 6. 归并（S3）

**第 1 层 · 服务端规则（零 LLM 成本）** —— 四步**有序**纯逻辑（顺序有意义，不可交换）：

1. **去重**：name 归一化（trim、折叠空白、全角空格）后「同名同类型 → 同一实体」；关系按 `(source, target, relation_type)` 去重 + **对称关系方向归一**（判据 = shared `RELATION_TYPE_META.symmetric`，单一定义，禁止手抄清单）。**此步不设阈值**——阈值要等别名归并后才有意义（别名合并会把章节集合变大）。
2. **应用别名归并**（§6 第 2 层的输出）：别名 → 规范名映射；合并章节集合；**关系端点同步重映射**并重新去重；丢弃自环关系。
3. **阈值**：人物与关系的跨章数 < `DECOMPOSE_MENTION_MIN_CHAPTERS` → 进 `filtered`（设定/地点不设阈值）。
4. **悬空关系过滤**（**端点存在性的唯一判据**——S2 不再预丢）：两端都必须落在**落库实体集合**内，否则丢弃并计入 `filtered`——既防模型幻觉出不存在的人物，也防阈值滤掉端点后留下悬空边。

关系表无唯一约束（`db/schema.md`），去重必须在代码里做。

**第 2 层 · 一次别名归并调用（只针对人物）**

- 输入 = 候选清单（规范名 + 出现章数 + 首次出现章 + 短摘要），**不是原文** ⇒ 成本与章数无关。
- 输出 = 合并组（规范名 + 别名列表 + 依据）。
- 服务端硬校验：组内每个名字**必须已存在于候选集合**（禁止发明新名字）；同一名字不得出现在两组；每组 ≥ 2 个名字；组大小 ≤ `DECOMPOSE_ALIAS_GROUP_MAX`；候选按提及次数截断 top `DECOMPOSE_ALIAS_CANDIDATE_MAX`（超出部分不参与合并）。
- **保守原则**（借 BookNLP 的教训：全共指会把不同实体错并成一个）：不确定 → **不合并**（宁可留重复）；缺依据的组直接丢弃；**只对人物做别名合并**，设定/地点只走第 1 层。

**第 3 层 · 落地形态**

- 实体 `name` = 规范名；其余别名写进 `description` 的「（又称：X、Y）」——UI 人物档案直接可见，**不动 schema**（把 `alias` 改成数组会牵动 Delta 标量口径、表单、AI 摘要、列表摘要）。
- `data.alias` 只填模型判定的主要化名。
- 报告里列出「已合并的别名组」供人工核对；修正路径 = 现成的人物详情编辑，**不做自动回滚**。
- **跨轮身份**：同名实体 / 关系**复用同一行**（不重复建）；跨轮「本轮未重现」的产物**不动**（不软删）——软删语义只归「本 job 自己写过、本轮重跑后消失」；拆解报告跨轮**更新同一条**（id 从历史清单取）。
- **增量更新**（续拆的「更新小说项目数据」）：`description` 取**更长者**（与 `entityDataOf` 的「最长的一条」同口径）、`personality` 取**并集**、`role` 本轮非空则更新、`gender` / `age` / `race` / `alias` **仅库内为空时填**、别名段「（又称：X、Y）」跨轮**合并**；结果无变化则不写（`updated_at` 同时是 baseline 比对依据）。

### 6.1 幂等、重跑与跨轮比对

`decompose_jobs.merge_written` 存本 job 上次归并写入的 `[{ id, type, updated_at }]`（实体 + 关系 + 报告）；**跨轮 baseline = 历史全部 job 的 `merge_written` 并集**（同一 id 取最新一次记录的时间戳）。重跑 S3 时三路比对：

| 情况 | 处理 |
| :--- | :--- |
| 新产物有、本 job 清单与 baseline 都没有 | 创建（库内同名行存在则**复用该行**，不重复建——`createEntity` 无同名守卫） |
| 新旧都有，且库内 `updated_at` **等于**清单 / baseline 记录值 | 复用 + 按上面的增量口径更新 |
| 新旧都有，但 `updated_at` **变了**（用户手工改过） | **不动**（用户编辑优先） |
| **跨轮**（baseline 有、本 job 清单没有）：新产物没有 | **不动**（不软删——续拆不是全量重算） |
| 本 job 清单里有、新产物没有 | `updated_at` 未变 → **实体：软删**（进回收站可还原）；**关系：物理删**（本仓关系无回收站路径，同手动删关系口径；产物重现时按新行重建）；变了 → 保留 + 报告里提示 |

**关系必须复用而不是新建**：`createRelation` 对同 `(source, target, type)` 判重抛 `RELATION_EXISTS`，而 S3 的落库与清单写在同一事务里 ⇒ 新建会打挂整轮 S3（续拆时首轮关系必然重现，这是必须成立的路径）。

**更新后必须刷新清单里的 `updated_at`**：否则下一轮比对会把我们自己的写入误判成「用户编辑过」，从此不再更新该行（跨轮尤其致命）。

`updated_at` 快照比对是本仓既有惯例（提案确认同款）。清单只是 id 列表，体积可忽略；**不给实体表加 provenance 列**。

### 6.2 拆解报告（S4）

落点：一条 `entities(reference)`——`name` = 「《书名》拆解报告」，`data.type` = `拆解报告`，`tags` = `["拆解报告"]`；正文进 `document_records`（服务端按行拆段落块，**不做 markdown 语义转换**，与参考资料导入同口径；标题块的升级路径见 `backlog.md`）。

内容六段（纯文本小标题 + 段落）：

1. 作品概览（章数 / 总字数 / 主要人物数 / 批数）；
2. 全书剧情摘要（用各章摘要做一次 map-reduce 调用）；
3. 人物小传汇总（每个落库人物的 `role` + `description` + 出现章范围）；
4. 结构与节奏（章字数分布、最长/最短章、疑似合并章）；
5. **已合并的别名组清单**（供人工核对）；
6. **被阈值滤掉的单章线索**（人物 / 关系——透明化，不静默丢弃）。

报告实体 id 记进 `merge_written` ⇒ 重跑时更新同一条，不重复建。

## 7. 生命周期与续拆

**状态机**：`pending → running → (paused | done | failed)`。批状态：`pending / running / done / failed`。

| 场景 | 行为 |
| :--- | :--- |
| 中止 | **每段**当前批跑完即停（在途 ≤ N；已发出的调用不 abort，结果不浪费），状态 `paused` |
| 续拆 | 跳过 `done` 的批，从第一个未完成批继续（批级幂等）；**段划分与并发数取 job 行快照**（配置改动只影响新 job），每段按段内已完成批重建自己的滚动累积 |
| **切书 / 关项目** | **自动暂停**（挂点 = `setCurrentProject` 单点，与 `disposeProjectRuntime` 同一处）——每段当前批跑完才停（同「中止」）。理由：项目切换会 `closeDatabase`，job 不能跨项目写数据；也不做「后台跨书跑」 |
| 服务端重启 | 残留 `running` 归一为 `paused`（进程内已无在跑 job），UI 提示「上次拆解中断，可续拆」 |
| **单批重跑** | `done` 与 `failed` 都可重跑：重算该批结果 → **必须重跑 S3（与 S4）**，否则库里是上一轮数据。成本 = 1 次抽取 + 1 次归并调用（S2 其他批不用重付） |
| 失败 | 批级失败不阻塞整个 job；失败批在进度页行内显示错误 + 可单独重跑 |

**S3 只在全部批完成后跑一次**（含重跑路径：任一批重跑后 job 回到 `running`，S3 重新执行）。

### 7.1 续拆 = 同一项目内开新 job

- **触发**：进度页完成态的「继续拆解」/ 概览页拆解卡（同一按钮）→ 不吃文件的预览与启动端点（`GET /decompose/plan` → `POST /decompose/continue`）。
- **已拆判定** = 历史上所有 job 的 `done` 批覆盖的章并集（`decompose_batches.status='done'`）。
- **默认范围** = 未拆章的**最小覆盖区间**；范围仍是**单区间**（`scope_start` / `scope_end`）—— 多段形态（如已拆 1–100 与 200–300）下默认会把中间的已拆章一起重拆；罕见且无数据风险（§6 的幂等与「用户编辑优先」兜底），代价只是几批 token。
- **显式范围含已拆章 = 有意重拆**：预览里标注「本范围含 N 章已拆（将重拆）」。
- **预览字数口径与首次预览可能差 1 批**：`plan` 从库内 `content_text` 投影长取字（= 真正喂模型的口径），`analyze` 从源切片 trim 长取字；不保留源文件就**无法同值**（估算实现同源，仅输入口径不同）。两个数字都只是预估，不追同值。
- **互斥**：存在 `running` / `paused` job 时不给开新 job（409 `DECOMPOSE_JOB_STATE`）。
- **历史 job 全部保留**（行与批结果都在 `data.db`），进度页只展示最新一个；更早的过程靠会话记录回看（§7.2）。
- **追加新章不在范围**：正文是 S1 全量导入的一次性产物；后续新增章节要正文增量导入——另属一个功能（`backlog.md`）。

### 7.2 拆解会话的保留上限

- 保留 `DECOMPOSE_KEPT_SESSIONS` **个 job 的全部**拆解会话（主 + worker 合计；按 job `created_at` 保留最近的，排序依据不取会话文件名——`job-<nanoid>` 里没有可解析时间）；**新一轮拆解创建会话之前**清理。
- 只删会话 id 为 `decompose-` 前缀、且其 job **不在跑**的记录：主会话按精确 id（`decompose-<jobId>`）命中、worker 按 `decompose-<jobId>-w` 前缀命中（查找走 pi 的磁盘发现——文件名带时间戳前缀，**不得**用文件名 glob）；**chat 会话永不参与自动清理**（用户资产）。
- 清理**不静默**：服务端日志 + 新一轮会话里记一条过程条目（`#/decompose` 时间线可见）；清理失败不阻塞拆解（同 `pruneBackups` 口径）。

## 8. 进度语义

- **进度面 = 专用路由页**（`#/decompose`），不是弹窗：任务跨分钟到小时、用户会离开或刷新，服务端持有 job 状态天然可恢复。
- **轮询**（`GET /api/v1/decompose/job`），状态进入终态即停。**不用 SSE**：不需要流式，且会撞 chat 的单在途流语义。
- 展示粒度 = 阶段条（5 段）+ 进度条（已完成批 / 总批数）+ 批次列表（可展开看该批抽取结果；展开是「核查后重跑」的前提）。
- **拆解记录时间线**（读 `GET /decompose/job/log`——**合并主会话与各 worker 会话**的过程条目、按时间排序；`batch_start` 带段号）：专记批表没有的信息——每次尝试的时间与失败原因（批表只留最后一次 `error` + 次数）、每步的模型与 token 用量、S3 归并 / S4 报告的明细与计数、每轮快照的组成摘要（`snapshot` 条目：人物 / 设定 / 地点 / 关系 / 前置摘要计数 + 预算省略告知；`batch_start` 条目带当轮快照规模）。批状态与批结果**不重复记**（批表是唯一真相）。
- **续拆入口**在完成态（§7.1）：「继续拆解」→ 范围与预估对话框（跳过「选文件」）。
- **不锁界面**：拆解期间用户可自由浏览大纲/正文/人物（数据实时写库）。理论上 S3 期间用户手工建同名实体可能撞 name 复用逻辑——边缘情况，不为此加锁（`backlog.md` 登记）。
- 书架行徽标只服务**当前打开的书**（`GET /project/list` 不含 job 状态；给每本书显示徽标要逐本开 `data.db`，不值得）——切书即暂停，所以「正在拆解」只可能发生在当前书上。

## 9. 不变式清单

1. **模型无写工具**：拆解全程模型只产出 JSON，落库由服务端确定性代码完成。
2. **章序 = 文件位置序**：编号只用于提示，永不参与排序。
3. **S2 不写业务表**：批结果只落 `decompose_batches.result`；业务数据只由 S3 写。
4. **重跑幂等**：同一份批结果跑两次 S3，库内实体/关系数量不变（`merge_written` 三路比对）。
5. **用户编辑优先**：`updated_at` 变化过的实体，重跑不覆盖、不软删。
6. **文档只读边界不破**：拆解写正文的唯一路径 = S1 的导入（用户文件 → 段落块），AI 侧工具面不变。
7. **状态与产物都在 `data.db`**：不新增项目目录（正文与实体均在库内），备份/导出/云自动携带。
8. **投影只能服务端派生**：正文 `content_text` 由服务端从块数组重算（同 `110-api-manuscript.md` 口径）。
9. **删除不静默**：切分阶段的目录页丢弃、超长块回扫无果、阈值滤掉的单章线索、会话保留上限的清理，一律在预览 / 报告 / 时间线里显式告知。
10. **跨轮不重复、不误删**：同名实体 / 关系复用同一行；跨轮未重现的产物不软删（软删只归本 job 重跑）；拆解报告跨轮更新同一条。
11. **每 turn 独立成根**：拆解会话的每个批 / 阶段 turn 都是新根，模型上下文只含本轮；自动压缩关闭。
12. **拆解会话只读**：`decompose-` 前缀的会话不可经 `POST /chat` 续聊（服务端拒绝）；有在途 job 时禁删。
13. **端点判据唯一**：关系端点存在性只在 S3 悬空过滤判定（按落库实体集合）；S2 抽取层不预丢，名字集合只服务提示词渲染。
14. **段内滚动、段间并集**：滚动累积只在段内生效，跨段一致性一律交 S3 全局归并；并发数在建 job 时快照，resume / 重跑按快照重算段。
