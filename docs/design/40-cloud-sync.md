# 云端存档（Cloud Sync）

> 定位：**可选的异地副本 + 多设备续写通道**。本地仍是唯一事实源，云端只是「另一块磁盘」加「两台机器之间的搬运工」。端点与字段契约见 `../api/100-api-cloud.md`；备份命名见 `../api/20-api-backup.md`；配置载体见 `config.md`；UI 形态见 `../ui/DESIGN.md`。

---

## 1. 为什么，以及不做什么

本地优先是本产品的第一原则（`00-master-design.md`）。云存档**不改变**它——它补的是两个本地磁盘解决不了的缺口：

1. **异地副本**：本机磁盘坏掉时，最近一次快照还在别人的机房里。
2. **多设备续写**：家里写到晚上，第二天在公司接着写同一本书。

**数据主权不变**：云端不是事实源、不参与任何在线能力（AI 对话、分析、计算全部本地完成）；不连云端时全部功能可用（离线可用是底线）；用户可以随时停用云存档并删除云端目录。

### 明确不做（YAGNI 登记）

| 不做 | 理由 | 升级路径（见 `backlog.md`） |
| :--- | :--- | :--- |
| 文件级/实体级自动双向合并 | `data.db` 是不透明二进制，两台机器各写一半无人能合并；真做要操作日志 + 因果时钟 + 墓碑，量级不对 | 拆存储或引入 CRDT（不做） |
| 自建后端服务 | 本仓是本地单进程应用，没有服务端运维位 | — |
| 内建端到端加密 | 密钥管理会砸掉「换机器填凭据就能续写」的核心体验（密钥存本机 → 新机器解不开；存云端 → 等于没加密） | 需要 E2E 的用户用 `rclone serve webdav` + `rclone crypt` 自建桥接：加密在用户侧完成，本仓零成本获得 |
| 云端书架（列云端全部书一键拉） | 只服务一次性的初始迁移；**现做「列 + 导入新书」**（§10），不做逐书冲突裁决与全量同步 | `backlog.md` |
| 增量上传（只传变化的文件） | WebDAV 无 delta；整包上传换来实现简单与「云端文件 = 本地文件逐字节拷贝」的干净模型 | `backlog.md`（包体积 = 三文件，已无 `sessions/` 膨胀源） |
| 多云端账户并存 / 云端存同步状态 | 一份配置 = 一个云盘；同步状态属「本机视角」，跨机器共享没有语义 | — |
| 自动重试 | 手动推送失败由用户点重试；自动推送失败等下一个 tick；关闭时推送失败只记日志 + 状态区标记 | — |

## 2. 传输层：只做 WebDAV

**只实现 WebDAV 一个协议**，不引任何云盘 SDK。

| 取舍 | 理由 |
| :--- | :--- |
| 为什么是 WebDAV | 坚果云原生支持（国内个人用户最现实的选择）；协议就是 `PROPFIND` / `MKCOL` / `PUT` / `GET` / `MOVE` / `DELETE` 六个动词 + Basic 认证，零 SDK、零 OAuth、零应用审核 |
| 其他云盘怎么办 | 用户自建桥接：`rclone serve webdav <remote>:<path>`（覆盖 OneDrive / Google Drive / S3 / SFTP / 阿里云盘等数十种后端）或 AList / OpenList（带 Web 界面，挂国内网盘并暴露 `/dav/`）。**适配负担在第三方**，本仓一行代码不写 |
| 为什么不做 S3 兼容 | 签名实现或重依赖（`@aws-sdk/client-s3`）；用户量级撑不起这份复杂度 |
| 为什么不做 OAuth 类（Dropbox / OneDrive 直连） | 纯本地应用无法保密 client secret，OAuth 应用注册与审核是长期运维负担 |
| 明文还是密文 | **明文上传**。用户主动选择上传即已把信任边界延伸到云盘厂商；半吊子加密只会制造「以为安全」的错觉。E2E 交给 `rclone crypt`（见 §1） |

**出站 HTTP 必须走全局 dispatcher**：服务启动时已安装（`packages/server/src/http-dispatcher.ts`，环境代理 + 连接族退避 + 空闲超时）。云存档**不得另建 fetch/agent**——否则丢失代理支持（真实故障场景见 v0.0.32 CHANGELOG）。

### 云盘侧的硬限制（实测口径，写文档与错误映射的依据）

| 限制 | 值 | 我们的对策 |
| :--- | :--- | :--- |
| 上传流量（免费账户） | 1GB / 月（下载不限） | 自动推送节流 2 小时 + 排除纯聊天触发（见 §5）；状态区显示上传大小并提示配额 |
| 单文件大小 | 500MB（WebDAV） | 推送前本地体积检查，超限直接拒绝（`CLOUD_BACKUP_TOO_LARGE`），不等服务器回 413 |
| 请求频率 | 600 次 / 30 分钟 | 无关（一次推送 ≈ 5–10 个请求） |
| 单次列出文件数 | 750（PROPFIND 分页） | 无关（书目录内最多几份备份） |

## 3. 同步单元：整包 zip + 乐观并发

**同步单元 = 备份 zip（`createBackupZip` 的产物：三文件——`project.json` / `outline.json` / `data.db`，正文与参考资料在 `data.db` 内）**。

**会话（`sessions/`）不进包**（2026-09 修订）：它是纯本地目录——聊天不改变创作数据，而一份含大幅重复内容的会话副本会让包体积不受控增长，且跨机器搬运聊天记录价值有限。代价：换机器/换创作根拉取后，聊天历史不跟随（对话本身在两台机器各自累积）；正文与实体的丢失面不交。

**推送 = 上传「某一份本地备份文件本身」**（逐字节拷贝、文件名原样），不重新打包、不转换格式。

- 好处一：云端文件 = 本地文件的拷贝，不存在两套格式或格式漂移。
- 好处二：手动命名过的备份（如「定稿」）原样上云，用户在云盘网页里一眼可辨。
- 好处三：下载回来可直接落进 `.backups/`（同款命名即可被列表与保留策略识别）。

### 冲突检测：head vs lastPushed

云端的「当前版本」= 该书目录内**文件名时间戳最大**的那一份（head）。本机在 `cloud.json` 记 `lastPushedFileName`（本机最后一次成功推送的云端文件名）。

```
推送 → PROPFIND 书目录 → head
  ├─ head 不存在（云端空）或 head == lastPushedFileName → 直接 PUT
  └─ head ≠ lastPushedFileName         → 另一台机器写过 → 409 CLOUD_CONFLICT
```

**为什么这样判定是健壮的**：比较的是 head 与 lastPushed，不依赖「文件是否还存在」——即便本机上次推的那份已被云端保留策略清掉，head 仍是**某台机器推送过的产物**，所以「不等于我的 lastPushed」始终等价于「别人写过」。**不需要时钟、不需要向量时钟、不需要锁**（两台机器不会被同一用户同时操作；WebDAV 无锁，理论竞态窗口存在但可接受）。

**已知边界（验证实测，接受并登记）**：

1. `head = 文件名时间戳最大者`，而时间戳来自**各机器本地时钟**。因此「另一台机器时钟偏慢、推送了时间戳更早的份」时 head 不变 → **漏报「云端有更新」**（不会覆盖别人，方向保守）。
2. `force`（强推）只写进本机那份，**不改变 head 的定义**：若云端存在时间戳更晚的他机份，强推后 head 仍是它 → 下一次推送会再次判冲突。出路是**拉取（接受对方版本）**或每次强推；这是「如实反映别人写过更晚的份」，不是缺陷。
3. 要让「head = 最近一次推送」严格成立，需要云端元数据（CAS/版本号）——WebDAV 无此能力，单独写旁路元数据文件不值（见 `backlog.md`）。**已给出可判定口径（本节三态表）**：判「云端有更新」用**云端文件集合**（`lastSeenCloudFiles`），与时间戳/时钟无关；`lastSeenHeadFileName` 仅作诊断快照（force 场景下它不等于真 head）。

### 三态状态机（UI 与一键同步的唯一依据）

| 云端有更新（云端**文件集合** ≠ `lastSeenCloudFiles`） | 本机有改动（创作数据 mtime > `lastSyncAt`） | 状态 | 可用动作 |
| :--- | :--- | :--- | :--- |
| 否 | 否 | 已同步 | 无（显示「已同步 · <时间>」） |
| 是 | 否 | 云端更新 | 拉取 |
| 否 | 是 | 有未同步改动 | 推送 |
| 是 | 是 | **冲突** | 裁决：保留云端 / 用本机强推 |

**为什么「云端有更新」用文件集合而不是 head**（定稿口径）：`head = 文件名时间戳最大者`，而时间戳来自**各机器本地时钟**——时钟偏慢那台推上来的份不会成为 head，用 head 比较会**漏报**「云端有更新」（见本节末尾「已知边界」）。用「书目录内的文件集合是否与 `lastSeenCloudFiles`（上次同步时记下的集合）相同」判定与时钟无关，也不会被保留策略清理误伤（清理后集合会重新记录）。

**「本机有改动」的 mtime 口径**：三文件 + `data.db-wal`——**不含 `.backups/`**（`force` 会把云端那份写进那里，不能算作创作改动）；**也不含 `sessions/`**（会话不进包，纯聊天不产生「有东西待推」）。**正文/参考资料写在 `data.db`，改动由 `data.db-wal` 天然涵盖。**
**容差只给 `data.db` 与 `data.db-wal`**（1s：备份/推送管道内的 `wal_checkpoint` 会把其 mtime 刷到同步时刻，严格比较会自激误判「永远有改动」）；`project.json` / `outline.json` **严格比较**——`lastSyncAt` 是不推进的固定基准，给它们容差会让「刚同步后 1 秒内的改动」被长期漏判（oracle 实测反例）。

**无同步记录时**（`lastSyncAt`/`lastSeenCloudFiles` 缺失）：本机按「有改动」处理；云端有份即视为「有更新」⇒ 两边都有 = **冲突**（保守：先让用户裁决，而不是静默覆盖任一侧）。

字段分工：`lastPushedFileName` = **冲突判定基准**（最后一次成功**同步**——推或拉——到的云端文件名）；`lastSeenHeadFileName` = 诊断快照（不参与判定）；`lastSeenCloudFiles` = 集合基准。

### 客户端接入（单一状态源、角标与一键动作）

**唯一状态源 = `packages/client/src/stores/cloud.ts`**（左栏「同步云端」与设置页云端面板是它的两个消费者）。两份消费者只持同一份 `status`——否则会出现「角标说冲突、面板说已同步」（两次独立请求、不同时刻的快照）。

| 关注点 | 口径 |
| :--- | :--- |
| **何时查状态（不轮询）** | 打开项目一次 / 每次点击「同步云端」/ 推送、拉取、保存配置之后。`/status` 每次 2–3 次 PROPFIND（无书目录 1、缓存命中 2、回退扫描 3），云盘免费配额 600 次/30 分钟——**没有定时器** |
| 并发合并 | 同一时刻的并发刷新合成一个请求（`in-flight` 去重）；动作在途时按钮 `loading` 防连点 |
| 角标语义 | 仅 `conflict`（error 语义色）/ `local-ahead` 与 `remote-ahead`（warning 语义色）亮；`unreachable` 与其余状态**不亮**（不变式 9：失败只轻提示） |
| 一键动作 | 见下「一键状态机」表——点一次 = 先实时复查状态，再按状态分派（不猜、不缓存旧判断） |
| 表单草稿 | 账号表单（url / 用户名 / 密码 / 设备名）**不进 store**：纯页内 UI 状态，切走即弃 |
| 跨页意图 | 「未配置 → 跳设置页并选中云端备份」经 store 的一次性意图下传（设置页 `backup-pane` 的选中态仍**不进 URL**，刷新回落默认项） |

**一键状态机（左栏按钮点击后的分派）**：

| 实时复查得到的状态 | 行为 |
| :--- | :--- |
| `unconfigured` | 置跨页意图 + 跳设置页（选中「备份 → 云端备份」），不 toast（落地页自带引导） |
| `no-project` | 按钮本就禁用（兜底：不动作、不报错） |
| `unreachable` | toast 错误文案（含 `errorCode`，强调本地功能不受影响）；角标不亮、不弹窗 |
| `synced` | toast「已是最新」 |
| `local-ahead` | 直接推送（缺省最新一份） |
| `remote-ahead` | 弹 `cloud-pull-confirm`（不直接拉——拉取会覆盖三文件） |
| `conflict` | 弹 `cloud-conflict-dialog`（两条路都要用户选） |

**为什么冲突要走对话框而不是自动合并**：三文件（`project.json` / `outline.json` / `data.db`）无法自动合并——任一侧静默取胜都会让另一侧的工作看起来「凭空消失」。对话框并排展示两份元信息，**两个选项等权**（都不用主色），并把「另一边会留档成哪一份本地备份」写清楚。

### 冲突裁决：两条路都把两边留成文件

| 选择 | 动作 | 结果 |
| :--- | :--- | :--- |
| 保留云端 | 本机当前状态自动快照进 `.backups/`（restore 管道既有行为）→ 应用云端那份（**`fileName` = 对话框里展示的那一份**，不是「服务端当下的 head」——两者在极端时序下可能不同） | 本机变了，本机旧状态留在本地备份里 |
| 用本机强推（force） | **先把云端那份 GET 下来**存进本地 `.backups/`（文件名原样）→ 再 PUT 本机那份 | 云端变了，云端旧状态留在本地备份里 |

**不变式：任何一条路径都不允许「一边被删且无留档」**。用户点错最坏结果是多出一份备份，不是丢数据。云端旧 head 在强推后仍留在云端目录里（由保留策略自然老化处理，带标签的除外）。

## 4. 拉取语义：三文件覆盖（会话不动）

**拉取与本地 restore 是两种语义，不能共用一套**：

| 操作 | 用户意图 | 语义 |
| :--- | :--- | :--- |
| 本地 restore（选自己的旧备份） | 「回到那个时间点」 | **三文件整体覆盖**（`overwriteProjectFiles`）；会话目录不触碰 |
| 云端 pull（同步另一台机器） | 「把那边的东西拿过来」 | **三文件覆盖**（含正文/参考资料——它们就在 `data.db` 里）；会话目录不触碰 |

**为什么会话不参与**（2026-09 修订）：会话不进任何 zip（§3），拉取的包里没有它 ⇒ 无从「写进来」也无从「删掉」。原先的 `sessions/` 并集（基线三方比较 + 删除优先 + `cloud.json` 的 `baseEntries`）随之取消——本机对话历史在 pull / restore / import 里一律**不写不删**（存量旧包内的 `sessions/**` 条目接受并忽略）。

**正文与参考资料走覆盖**：它们是同一个库里的结构化数据，与大纲/实体/Delta 同为「覆盖」组（原先随目录并集的 `references/` 已废弃）。**已知代价（接受）**：另一台未推送的结构化改动会被云端那份覆盖——这就是「覆盖组」的固有代价，覆盖前自动快照是后悔药。

### 删除一本书（本地 + 云端）

| 层次 | 行为 |
| :--- | :--- |
| 本机删书 | `POST /project/delete`：删目录（含该书 `.backups/`）。**删前若该书有同步记录**（`cloud.json` 有 book state）→ 先推一份最新状态上云（纯本地判据、不查网络）；推送失败默认**中止删除**，`force` 才继续 |
| 云端那几份 | 默认**原样保留**（提示用户可在云盘网页删除）；删除确认框勾选「同时删除云端备份」才删云端目录并清 `cloud.json` state（best-effort：失败不改变本地已删的结果） |
| 不可逆 | 本地 `.backups/` 在该书目录内，随目录一起消失；删前那次推送是唯一「不在同一磁盘上的副本」保障 |

**不变式：删书前必有一次落地的云端副本，或用户明确的 `force`**——不允许静默把最新状态连同本地副本一起丢掉。

## 5. 触发口径（自动推送）

`autoPush` 是**本机级**开关（`cloud.json`，缺省关）——每台机器的联网环境与配额不同（家里台式机可以自动推、笔记本手动推），因此不随书走（对比：备份频率随书，在 `project.json`）。

| 触发 | 变更判定 | 节流 | 推的内容 |
| :--- | :--- | :--- | :--- |
| 自动定时 | **只看创作数据**（`data.db`（含正文/参考资料）/ `data.db-wal` / `outline.json` / `AGENTS.md`；**`sessions/` 恒不参与**——会话不进包） | ≥ 2 小时（写死常量） | 最新一份本地备份 |
| 关闭项目时 | **同款三文件变更判定**，且**最新备份已涵盖这些变更**（有未备份改动 → 跳过） | 无 | 最新一份本地备份 |
| 手动备份成功后 | 无条件 | 无 | 刚生成的那份 |
| 手动点「同步云端」 | 无条件（**但 `local.backupStale` 时先弹 `cloud-stale-backup-dialog` 二选一**，见上「职责分离」） | 无 | 默认最新一份 |
| 面板「推送」/ 旧包确认框「上传旧备份」 | 无条件（用户已明确选择） | 无 | 默认最新一份 |

**排程口径（定稿口径，单一定时器）**：自动推送**不新起定时器**，挂在现有自动备份的 `setTimeout` tick 链上——排程条件 = 「自动备份频率开启」**或**「`autoPush` 开启」：

| 自动备份频率 | `autoPush` | tick 间隔 | 效果 |
| :--- | :--- | :--- | :--- |
| 开启（如 10 分钟） | 开 | 备份频率 | 每次 tick 各判一次：备份看「任何变更」、推送看「创作数据变更 × 2h 节流」 |
| 关闭（null/0） | 开 | **2 小时**（= `AUTO_PUSH_THROTTLE_MS`） | 只跑推送判定（备份判定在频率关闭时本就返回 false） |
| 任意 | 关 | 仅随备份频率 | 只有备份，没有任何推送 |
| 关闭 | 关 | 不排程 | — |

**为什么「关掉自动备份」不等于「关掉自动推送」**：两者的动机不同（前者常是「不想频繁写盘」，后者是「换机器时少点手动」）——若让自动推送跟着备份频率一起静默失效，设置页那个开着的「自动推送」开关就是在说谎。

**状态位 `backupStale`**（`GET /cloud/status` 的 `local` 段）：= 「最新一份本地备份早于最新创作改动（三文件口径）」**且**「确有未同步改动（`local.dirty`）」——两个条件缺一不可。为什么加后一半：拉取/恢复会用**刚生成的覆盖前快照**（时间戳早于写入）当最新备份，只看 mtime 会立刻误报「有改动未进最新备份」（用户真机实测）；加了 `dirty` 之后，「拉取刚写完」与「用户真改了东西」被区分开。**注意自动路径的守卫用的是纯 `hasUnbackedChanges`**（不叠 `dirty`）：那边必须严格——最新备份确实落后于本机状态就不能推，否则会把旧内容推上云。它**不随同步前移**——推完旧包后 `state` 会变 `synced`，但 `backupStale` 仍为真（这正是它存在的原因：把「已同步」与「内容不落后」分开表达）。

**节流基准 = `lastAutoPushAt`**（`cloud.json` 的 book state，**只有自动路径推进**）：手动推送不推进它（手动路径无条件触发，不占节流额度），关闭项目那次也不推进（那是「工作段结束」语义，与 2 小时节流无关）。

**职责分离（定稿口径）**：**云端永不创建备份**——自动路径不做「按需备份」，只推**已存在的本地备份**（备份机制归本地，云端只是那份 zip 的镜像）。
**自动路径遇「本机有改动未进最新备份」→ 跳过不推**（用户选定 (ii)）：若最新一份本地备份早于最新创作改动，定时与关闭项目路径**直接返回**——不推旧包、**不写 `lastAutoPushError`**（这不是失败，是还没到能推的状态），只让状态位 `backupStale` 亮着；用户主动点「同步云端」时由对话框让他选「立即手动备份并推送」或「上传旧备份」。
**为什么不让自动化静默推旧包**：推旧包会把 `lastSyncAt` 前移到 now，三态随即显示「已同步」，而云端内容落后于本机——换台机器拉下去会把它自己更新的三文件覆盖掉（有覆盖前快照兜底，但用户看到的是「内容缩水」）。宁可让自动推送在这个形态下暂停，也不要让 UI 撒谎。
**自动路径失败只记日志 + 状态标记**：`lastAutoPushError`（`{ code, message, at }`）写进 book state 并由 `GET /cloud/status` 的 `local` 段透出（设置页面板显示一行），**不弹窗、不阻塞请求**——关闭项目那次尤其如此（fire-and-forget：网络差时一次 push 可能数秒，不能拖住关闭）。
**清除点单点化（oracle 反例 4 收口）**：该标记的**唯一清除点 = `pushBackup` 的成功写**（`lastAutoPushError: undefined`）——口径是「最近一次自动推送失败」，**任何一次推送成功**都证明它已过期；若只让自动路径清，用户手动推送成功后面板会常驻一行过期提示。`CLOUD_CONFLICT` 这类需要人裁决的失败，面板那行会补一句行动指引（手动推送 / 裁决框里选「用本机覆盖云端」）。

**为什么 `sessions/` 恒不参与触发**：它不进包（§3）——没东西可推。纯聊天时段既不产生备份也不烧配额；代价是聊天历史不跨机器。

**关闭项目时为何不再是「更宽」的触发**：既然会话不进包，「工作段结束」与定时触发的判定就是同一份三文件口径（原先多出来的只有聊天变更）。

**为什么 2 小时是写死常量**：它与 SSE 心跳间隔、提案 TTL 同类——**失控保护类数值不给用户配**（能配就等于允许拆掉保险丝，见 `config.md` 的可配 / 不可配判据）。

## 6. 云端布局、保留与上传

```
<webdav.url>/                       例：https://dav.jianguoyun.com/dav（**用户填的云盘根**）
└── ai-editor/                      **工作根**：由云端对接层唯一拼接（用户不需要知道）
└── <书名>-<完整 projectId>/         例：斗破苍穹-proj-V1StGXR8Z5jdHi6BmyT4
    ├── 20260813-101530123-自动-苹果本-人物32-设定58-章120.zip
    ├── 20260813-181200400-手动-苹果本-定稿-人物32-设定58-章120.zip
    └── .tmp-…                       （上传中/中断遗留，下次推送前清理）
```

**目录名用完整 `projectId`（不是短前缀）**：两本同名书 + 短 id 碰撞会把两本书写进同一目录（数据交叉）；完整 id 零成本消掉这个风险。`projectId` 是跨机器稳定的身份（`project.json` 的 `id`，导入/恢复按它分流）。

**书目录定位按 id 匹配，不按书名拼路径**（书名会改，机器之间也可能不一致）：`cloud.json` 缓存 `dirName` 走快路径；`PROPFIND` 命中 404 时回退扫描云端根目录、按目录名后缀匹配 `-<projectId>`，并按匹配结果修正缓存。

**书名重命名 → 云端目录 `MOVE`**（`POST /project/rename` 的分支）：WebDAV `MOVE` 是同目录/跨目录 rename，原子且保留目录内文件。云端目录名随后一次改名者变化（两台机器书名不一致时亦然），身份仍由 id 保证。

**探测目录的删除**：`/cloud/test` 的探针目录用 `removeDir`（集合删除需**尾斜杠 + `Depth: infinity`**，RFC 4918 §9.6.1；缺了部分服务器会重定向或拒绝，留下空目录），并在每次测试开始时**先清上一次的残留**（失败只记日志——空目录无害，下次再清）。

**目录名回退链（坚果云实测）**：部分云盘对**单段名字长度**的限制远严于文档里的 255 字符路径上限——坚果云对 MKCOL 返回 `400 IllegalArgument / sandbox name is too long`。因此建书目录按候选链逐个尝试：`<书名>-<id>`（默认，便于在云盘里辨认）→ `ai-editor-<id>` → **`<id>`**（最短且一定含 id）；任一步成功即采用，并把**实际生效的目录名**写进 `cloud.json` 的 `dirName`。三个候选都以完整 id 结尾/相等，故回退扫描（`name === id || name.endsWith('-'+id)`）始终能重新定位。

### 保留策略

| 规则 | 值 |
| :--- | :--- |
| 保留份数 | 最近 **5** 份（云端是异地副本，不是历史归档——**主历史在本地 20 份**） |
| 豁免 | **带用户标签的备份永不清理**（标签是用户唯一的意图通道，自动删掉它等于告诉用户别起名） |
| 可删范围 | **只删**「能解析出时间戳」（`parseBackupFileName` 通过）且**不带用户标签**的份——云目录里用户手工放的东西一律不碰，认不出就不删；`.tmp-` 垃圾属 §6 上传流程第 2 步（推送前清理），不归保留策略 |
| 时机 | **只在推送成功后**执行；清理失败不阻塞推送 |
| 删除对象 | 最旧的那批（绝不删 head），故「删错」最坏是丢一个旧时间点 |

### 上传：临时名 + MOVE

**重复推送是幂等的**（坚果云真机实测补的）：目标是同一份备份时，
① **已存在同名同大小的份 → 直接跳过上传**（用户连点、自动推送重试、上次推完又推）——省云盘配额，也避开
「目标已存在」在部分云盘上的 MOVE 语义差异（坚果云即使带 `Overwrite: T` 仍回 `409 DuplicateName`）；
② 万一仍撞上（如大小不同/服务端状态不一致），`MOVE` 收到 `409/412` 时**先删目标再重试一次**——
目标就是被覆盖的那一份，删掉不会损失别的东西。


1. `PROPFIND` 书目录（不存在 → `MKCOL` 幂等创建）→ 清理自己遗留的 `.tmp-*`
2. **体积检查**：zip > 500MB → 拒绝（`CLOUD_BACKUP_TOO_LARGE`）
3. `PUT` 到 `.tmp-<正式文件名>` → 成功 → `MOVE` 成正式名

**为什么必须两段**：`PUT` 失败/超时会在云端留下**半截 zip**，而它一旦占住正式文件名就会被当成有效备份（下载后校验失败 = 用户以为备份坏了）。临时名 + 原子 `MOVE` 保证正式名下的文件永远是完整包；中断最坏留一个 `.tmp-` 垃圾，由下次推送清理。

**唯一载体**：`<创作根>/.ai-editor/cloud.json`，创建时权限 `0600`（与 `config.json` 同目录、不同文件）。

```json
{
  "webdav": { "url": "…", "username": "…", "password": "…", "device": "苹果本" },
  "autoPush": false,

    "proj-V1StGXR8Z5jdHi6BmyT4": {
      "dirName": "斗破苍穹-proj-V1StGXR8Z5jdHi6BmyT4",
      "lastPushedFileName": "…",      // 冲突判定基准（推/拉后都更新）
      "lastSeenHeadFileName": "…",    // 诊断快照（不参与判定）
      "lastSyncAt": "2026-08-13T10:15:30.123+08:00",
      "lastSeenCloudFiles": ["20260813-101530123-自动-苹果本-人物32-设定58-章120.zip"],
      "lastAutoPushAt": "2026-08-13T10:15:30.123+08:00",   // 自动推送节流基准（仅自动路径推进）
      "lastAutoPushError": { "code": "CLOUD_UNREACHABLE", "message": "…", "at": "…" }  // 自动路径最近一次失败（有则显示，成功即清）
    }

```

| 决策 | 理由 |
| :--- | :--- |
| 独立文件（不并进 `config.json`） | ① 凭据与偏好分离：`config.json` 的语义是「用户可手编」（`debug` 段）且会被贴进 issue，凭据物理上不该在那条路径上；② `0600` 只加给一个文件，不必给手编文件降权限；③ `config.json` 已有「手编 / 服务端合并写」两套语义，再塞凭据会污染 |
| 明文 | Node 无内置系统钥匙串 API；为此引依赖（`keytar` 已废弃维护）不值得。云盘侧用的是**应用密码**（可单独吊销，不是账号主密码），泄露面可控。UI 明说「凭据以明文保存在本机 `.ai-editor/cloud.json`（权限 600）」 |
| `autoPush` 在此（不在 `project.json`） | 本机属性（联网环境/配额因机而异），不随书、不随备份回滚 |
| `books` 按 `project.id` 键控 | id 跨机器稳定；天然每台机器一份状态。**旧文件里的 `baseEntries` 字段读侧容忍但不使用**（2026-09 会话不进包后已停写） |
| 不做环境变量 / `!命令` 兜底 | 那是 pi `auth.json` 的 `resolveConfigValue` 语义，本场景没有需求面 |

**凭据绝不进项目文件**（铁律，`config.md`）：`project.json` / `outline.json` / `data.db` / `sessions/` / 备份 zip **天然不含**任何云盘凭据。

**凭据也不得进文件名段**（2026-09 安全修复）：备份文件名里的**设备段**（`webdav.device`）与**标签段**（手动备份名称）都会本机落盘、上传云盘、并在冲突裁决框展示——值等于应用密码即等于把凭据广播出去（真实事故：用户误把应用密码贴进设置页「设备名」框，云端出现 `20260917-071459587-手动-<应用密码>-人物2-设定37-章9.zip`；语法规则对 16 位小写字母数字的坚果云应用密码完全放行，所以必须单独挡一道）。口径（唯一比较函数 `cloud/state.ts` `equalsCredential`，原值 + `trim()`）：

| 位置 | 行为 |
| :--- | :--- |
| 写入侧 `PUT /cloud/config`（`writeCloudConfig`） | 设备名 == 生效密码 → 400 `VALIDATION_ERROR`，整请求零落盘（同一请求里新设的密码 + 新设备名一起挡） |
| 写入侧 `POST /backup`、`POST /backup/rename`（`backup.ts`） | 标签 == 已保存密码 → 400 `VALIDATION_ERROR`，不产出/不改名 |
| 读取侧 `configuredDeviceName` | 存量坏值（含手工编辑/旧版本写入）按**未配置**处理 → 回退 hostname 派生值，**立刻止漏**（`deviceConfigured` 随之 false，设置页不预填坏值） |

已泄露到云端的旧文件名本程序**不自动清理**（那是用户的备份数据）——用户侧处置 = 轮换云盘应用密码（旧值当场作废）+ 删/改那份文件。

**已知弱点（接受）**：创作根换位置或换机器 → 同步状态丢失 → 表现为「提示需要裁决一次」；**不丢数据**，方向保守。

## 8. 不变式（实现与验证的依据）

1. **云端不是事实源**：所有功能在离线状态可用；云存档的任何失败都不得阻塞打开/关闭/编辑/备份。
2. **凭据不进项目文件、不进 zip、不进任何 API 响应**（`GET /status` 与 `PUT /config` 的响应必须剔除 password）。
3. **正式文件名下永远是完整包**（临时名 + `MOVE`）。
4. **任何冲突路径都不允许一边被删且无留档**（拉取先快照本机；强推先下载云端）。
5. **删除的语义**：会话不进云端，因此不存在「拉取复活已删会话」的问题；**删书**（`POST /project/delete`）前必有一份落地云端副本或用户明确的 `force`（§4）。
6. **只删自己认识的份**（时间戳格式 + 无标签），且只在推送成功后；`.tmp-` 垃圾由推送前清理负责。
7. **书名变化不影响云端定位**（按 id 匹配 + 回退扫描），改名后云端目录 `MOVE`。
8. **书目录名含完整 `projectId`**（身份唯一，不靠书名区分）。
9. **打开项目时的后台检查失败只记日志**（状态区显示「未连接」/ 角标不带待办），**绝不弹窗**——离线可用优先。
10. **自动推送不是无条件的**：必须同时满足「节流间隔」与「变更」两个条件（关闭项目与手动触发除外）。

## 9. 失败语义

| 场景 | code | UI |
| :--- | :--- | :--- |
| 未配置就调用需要云端的动作 | `CLOUD_NOT_CONFIGURED`（409） | 「未配置云盘」→ 引导进设置页云端面板 |
| 上游 401/403（凭据被吊销、应用密码错误、权限不足） | `CLOUD_AUTH_FAILED`（502） | 「云盘认证失败，请检查用户名/应用密码」，不自动重试 |
| 网络不可达 / DNS / TLS / 超时 / 上游 5xx | `CLOUD_UNREACHABLE`（502） | 「无法连接云盘（…）：<底层原因>」（**带上底层错误码**：普通 Error 取 `cause.code`，undici 多地址聚合失败时取 `cause.errors[].code` 并**去重合并展示**（如 `ECONNREFUSED/ETIMEDOUT`）——否则文案退化成无信息量的 `fetch failed`） |
| 上游 507 / 配额提示（流量或容量耗尽） | `CLOUD_QUOTA_EXCEEDED`（502） | 「云盘空间或上传流量已用尽」（提示免费账户 1GB/月） |
| zip 超过单文件上限（本地先判） | `CLOUD_BACKUP_TOO_LARGE`（400） | 「备份包 N MB 超过云盘单文件上限 500MB，未推送」 |
| 推送时 head ≠ lastPushed | `CLOUD_CONFLICT`（409） | 弹出裁决 |
| 拉取指定的云端文件不存在 | `CLOUD_FILE_NOT_FOUND`（404） | 「那份备份已不存在，请刷新状态」 |
| 导入的云端书在本机已有同 id | `PROJECT_ALREADY_EXISTS`（409） | 「本机已有这本书，打开后同步即可」 |

**上游 404（书目录不存在）不是错误**：推送前 `MKCOL` 幂等创建。错误码登记见 `../api/error-code.md`（服务端扩展码）。
**地址语义 = 用户的云盘根**（如 `https://dav.jianguoyun.com/dav`）：**工作根 `<云盘根>/ai-editor/` 由云端对接层唯一拼接**（`createWebdavClient` 内一处常量），书目录建在工作根之下。好处：设计语义留在应用侧——`cloud.json` 与设置页都只表达「用户云盘根」，用户不必知道我们的目录约定，云盘根也不会散落书籍目录。**没有「截断再拼回」的迁移分支**：无论前端传什么，一律在其后追加一段 `ai-editor`。地址若还不存在（用户随手写的路径）→ `ensureWorkingRoot()` 幂等创建「云盘根 + 工作根」自愈。

**根目录通常不可写文件**：坚果云等云盘允许在根下**建目录**，但**直接 PUT 文件到根**会 404 `ObjectNotFound`。因此 `/cloud/test` 的写探针先建一个工作子目录（`.tmp-ai-editor-writetest-dir/`）再写文件，成功路径连子目录一起清掉；建不出子目录（不支持/权限不足）才退回根目录写法。

**`PROPFIND` 空 multistatus = 路径不存在**（坚果云实测）：部分服务器对**不存在**的集合回 `207` + 空 body 而不是 `404`。`list()` 先看**原始**条目数——`0` ⇒ 不存在（返回 `null`，交给调用方 `MKCOL`），`≥1` ⇒ 存在（存在但空目录也有自身条目，过滤后得 `[]`）。误判的代价很大：把它当「存在但空」会跳过建目录，后续 `PUT` 才报 `404 ObjectNotFound`，看着像写权限问题。

**`MKCOL` 不带尾斜杠**（RFC 4918 §9.3.1 示例形态）：带尾斜杠时部分服务器（实测坚果云）回 **405「已存在」却并不创建**——调用方以为目录就绪，后续 `PUT` 才 404，错误错位到写权限上去。配套：`/cloud/test` 在「列不出来 → MKCOL」之后**复核一次**，仍不存在则报「云盘目录不存在且创建失败：<地址>（确认地址指向 WebDAV 根目录）」，而不是让用户看到 PUT 404。

**「可写不可删」的云盘不报认证失败**：`/cloud/test` 的写测试文件删除失败（DELETE 403/405 等）**不降级为 `CLOUD_AUTH_FAILED`**——凭据本身是好的，读 + 写都通过了，只是清理失败；返回成功并在文案里说明「已在云盘根目录留下 `.tmp-` 测试文件，可手动删除」（删除失败的具体状态码进日志）。反过来说：`PUT` 失败才是真的写权限问题（`AUTH_FAILED`）。
**代价（登记）**：DELETE 受限的云盘上，保留策略清理与 `.tmp-*` 清理也只会 `console.error` 并放行（设计如此：清理失败不阻塞推送）——表现是**份数不收敛**（可能堆到配额上限）与临时文件残留，靠下次推送重试；`/cloud/test` 的文案只提示测试文件残留，不覆盖这条。

## 10. 新机器恢复（列云端书 + 导入为新书）

**问题**：`cloud.json` 在**创作根**（不随书走、不进备份），新电脑上是空的 → 没有已打开项目 → `/cloud/pull` 不可用。而云端每书一个目录、每目录多份备份，手动在网页里翻目录下载是唯一旧路径——多书时体验差。

**口径：只做「列 + 导入新书」的一次性迁移面**，不做云端书架全量同步（逐书冲突裁决、一键拉全部、云端删除传播——YAGNI，见 §1）：

| 端点 | 做什么 |
| :--- | :--- |
| `GET /cloud/remote-books` | `PROPFIND` 工作根 → 列每书的目录名/解析出的书名与 `projectId`/可解析备份（head 时间、份数、大小）/`localExists`。工作根不存在 → 空列表（**不写云盘**） |
| `POST /cloud/import-book` | 下载该目录 head（或指定份）→ **目录名解析出的 id 与包内 id 不符 → 拒绝**（防把书写进别的书的云端目录）→ `validateBackupPackage`（与 `POST /project/import` 同一实现）→ 本机已有同 id → 409 → `uniqueBookDir` 建档（**id 沿用**）→ zip 原样落新书 `.backups/` → 写 `cloud.json` 同步状态 |

**三条为什么这样定**：

1. **导入必须写同步状态**（`lastPushedFileName` = 导入的那份 / `lastSeenCloudFiles` = 当时云端集合 / `lastSyncAt` = `max(now, 三文件 mtime 向上取整到毫秒)`——基准不由自己刚写的文件决定，否则导入完立刻查状态会因「毫秒截断 vs 亚毫秒 mtime」被读成 `local-ahead`）：不写，新机器第一次打开这本书就是 `conflict`（云端有份 + 本机无同步记录）——刚拉下来就逼用户裁决，荒谬。写入后状态即「已同步」，后续推送/拉取正常。
2. **导入 = 建新书（不自动打开、不合并）**：机器上本来就没有这本书，没有可合并的对象；语义与「导入备份」完全一致（同一校验管道、同一条建目录路径）。本机已有同 id → 拒绝（那本书应该在应用内自己同步，不走导入）。
3. **那份 zip 要落到 `.backups/`**：否则新机器上「最新一份本地备份」是空的，`backupStale`/旧包确认框等本地备份语义会立刻报「还没有备份」。落一份后，本地备份链从「刚才拉下来的那份」开始。

**备份侧不做「一键推整架」**（同 2026-09 口径）：每本书在打开时自动/手动推送；没打开过的书没上云是事实，用户逐本打开推一次即可。整架推送要遍历书架并为未打开的书临时开 `data.db` 打包，属新一档复杂度，诉求出现再排（`backlog.md`）。
